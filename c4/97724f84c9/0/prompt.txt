## 1. Save format

**Schema:** `SaveData` = **version 16**, defined `lib/game/types.ts:353` (`export type SaveData = Omit&lt;SaveDataV15,"version"&gt; &amp; {...}`; the full V1→V15 chain is above it). Worldgen baseline = **`WORLDGEN_VERSION = 10`** (`lib/game/config.ts:353`).

Produced by `GameEngine.serialize()` (`lib/game/engine/GameEngine.ts:745-778`). Fields:
- `seed`, `worldType`, `gameMode`, `difficulty`, `hardcore`, `gameOver`
- `changes: Array&lt;[blockIndex, blockId]&gt;` — the **block diff vs generated terrain** (`types.ts:147`); edits that revert to baseline are pruned
- `inventorySlots: SavedSlot[]` (36 slots; `{id,count,durability?,enchantments?,customName?}`), `equippedArmor`, `selectedSlot`
- `player {x,y,z}`, `dayClock`, `hearts`, `hunger`, `spawnPoint`
- `blockEntities` (chest contents keyed by voxel index), `lootedChests` (worldgen loot chest indices)
- `effects`, `xp`, `stats`, `advancements`, `mobs` (only tamed pets + villagers), `vehicles` (≤`MAX_VEHICLES`=64)
- `villagesSeeded: true` (serialize adds this at `GameEngine.ts:776` — a boot flag, not in the docs list)

**Encoding/size:** plain `JSON.stringify` — `writeSave` is literally `storage.setItem(key, JSON.stringify(data))` (`lib/game/save.ts:307-309`). **No compression, no RLE, no base64.** Size is dominated by `changes` (one `[int,int]` pair per player-edited voxel). Light is never serialized (derived cache, rebaked by `computeFullLight`, `GameEngine.ts:201`). So a lightly-edited world is a few KB; a heavily terraformed one can grow unboundedly as raw JSON — relevant for cloud-sync payload limits.

**Save/load/autosave code map:**
- `readSave(saveKey, storage=localStorage)` / `writeSave(...)` — `lib/game/save.ts:227` / `:307`
- Restore validators (all in `save.ts`): `restoreSlot`, `restoreInventorySlots`, `restoreEquippedArmor`, `restoreEffects`, `restoreStats`, `restoreMobs`, `restoreVehicles`, `restorePlayerPosition`, `restoreGameMode/Difficulty/Hardcore/GameOver`, etc.
- Engine restore on boot: `GameEngine` constructor `lib/game/engine/GameEngine.ts:175-201` (regenerates from seed, then `blockChanges.applySavedChanges(save.changes)`)
- **Autosave** — all in `lib/game/useMinecraftGame.ts`: `persistGame()` helper (`:83`); `setInterval(autoSave, AUTOSAVE_INTERVAL_MS)` (`:281`, `AUTOSAVE_INTERVAL_MS=15000` from `config.ts:336`); `beforeunload` (`:282`); unmount save (`:384`); hardcore game-over immediate persist (`:319`); `quitToWorlds` synchronous save (`:509`)
- Manual controls: `saveNow`/`loadNow`/`resetNow` (`useMinecraftGame.ts:480-505`), wired to `PauseMenu` buttons

**Migration:** `readSave` runs a linear chain `migrateSaveV1toV2 … migrateSaveV15toV16` (`save.ts:53-224`, invoked `:264-279`). Most steps are pure version bumps; **V1→V2** (40→36 slots, repack) and **V11→V12** (armor to dedicated storage) do real transforms. Unknown/future versions → `null` (treated as no save). **Worldgen** migration is orthogonal and per-world: if a world's stored `worldgenVersion` ≠ current `WORLDGEN_VERSION`, its block-diffs are discarded and it reboots from seed (`lib/game/worlds.ts`, see `sanitizeWorld:107`).

**Every storage function takes an injectable `Storage` param** — this is the natural seam to redirect at a cloud backend.

# Headless Simulation Core Extraction — Feasibility Assessment

## Headline

**This engine is already a headless simulation core.** It was architected headless-first: the entire simulation lives in `lib/game/engine/` + `lib/world/`, runs under `bun test` with no DOM, and the docs state it explicitly (`docs/architecture.md:16`, `GameEngine.ts:151-156`, `state.ts` header). Rendering (three.js), audio (WebAudio), input (DOM listeners), and React are strictly separated observer layers. **Extraction to Node/Bun is low-effort mechanically; the real work is not decoupling from the browser — it's that the state model is single-player-shaped.**

## 2. Game loop / step-tick pipeline

- **The engine is NOT frame-coupled.** `GameEngine.step(dt, input)` is a plain function of `dt` seconds (`GameEngine.ts:361`). The `requestAnimationFrame` loop lives **only** in the React hook `lib/game/useMinecraftGame.ts:297-374`, which does bounded catch-up substepping: accumulate wall-time, then `while (pending&gt;0) step(min(pending, 0.05))` — `MAX_STEP_SECONDS=0.05` (20 Hz cap), `MAX_SUBSTEPS=5`. A server replaces this with a `setInterval`/timer driving the same `step(dt)`; nothing in the engine changes.
- **Step order** (`GameEngine.step`, documented at `docs/architecture.md:41-56`, code at `GameEngine.ts:361-449`):
  0. pause gate (freeze + snapshot, return)
  1. stuck detection / auto-unstuck
  2. death check + respawn countdown (while dead: only mobs, TNT, projectiles tick)
  3. sleep gate (freeze during fade, then skip to morning)
  4. player OR mounted-vehicle motion (`playerMotion`/`vehicles`)
  5. hunger / regen / water / lava / oxygen / starvation (`playerStats`)
  6. status effects tick
  7. mining progress + block break/place (`mining`)
  8. thrown spears, fishing
  9. day-night clock → weather (transient, seed+dayClock)
  10. random block ticks (crop growth)
  11. hostile / aquatic / dungeon-spawner directors (`spawnDirector`)
  12. mob AI (`mobAI`)
  13. primed TNT, projectiles (`projectileAI`)
  14. breeding, raid
  15. debug readout → `refreshSnapshot()`
- **Determinism:** the sim's own randomness is an injectable `rng` (`GameEngine.ts:177`, default `Math.random`) threaded through mob AI, spawns, loot, fishing, breeding. Worldgen is fully deterministic (see §4). So the engine is deterministic **if** you inject a seeded PRNG — the seam already exists, but the default is `Math.random`. There is no wall-clock (`Date.now`/`performance.now`) or frame counter inside the engine; all time flows through `dt`.

## 4. Worldgen

- **Fully deterministic and seeded.** `generateWorld(world, worldType)` (`lib/world/generation.ts:154`) runs terrain → caves → ores → lava → trees → structures → villages → dungeons, each pass using its **own named mulberry32 PRNG** derived from `world.seed` (`0x6d2b79f5` mulberry constant at `generation.ts:157`; separate streams `coalRand`, `dungeonRand`, `villageRand`, `shipwreckRand`, `treasureRand` so passes stay byte-identical). Terrain height uses `smoothNoise2D(x,z,seed)` (`generation.ts:141`).
- **Byte-identical output per seed is a hard save-format contract**, pinned by hash tests in `generation.test.ts` (`docs/architecture.md:130`). This is gold for multiplayer: a joining client regenerates the identical baseline from `seed` alone, so you only ship the **block diff**, not 37 MB.
- **NOT chunked / not on-demand.** The whole world is generated at engine construction (`GameEngine.ts:185`). World is fixed **512×512×150 = 39.3 M voxels ≈ 37 MB `Uint8Array`** for blocks + an equal-size light array, all baked at boot (`computeFullLight`, `GameEngine.ts:201`). There is no chunk streaming, no partial load, no interest management. Dungeon/shipwreck/treasure/village sites are re-derived from seed at boot (`collect*Sites`).

---

## 5. Player action flow &amp; physics

Flow: **DOM event → `inputController` → `engine.dispatch(Command)` or `engine.applyLook(dYaw,dPitch)` → system module mutates `GameState`.**
- Continuous movement is a `FrameInput` (`state.ts:307`): `{ keys: Set&lt;string&gt;, capsActive, leftMouseHeld, pointerLocked }` read every `step`. Keys are raw KeyboardEvent codes (`"KeyW"`,`"Space"`,`"KeyC"` — see `playerMotion.ts:77-80`). Discrete actions (`attack`, `placeBlock`, `selectSlot`, `eatFood`, `craft`…) are `Command`s dispatched immediately (`inputController.ts`).
- **Physics/collision** is in `systems/playerMotion.ts` — swept axis-by-axis collision via `collidesAt` (`lib/world/queries.ts`), gravity/jump/fly/noclip, fall damage, void damage, world-border clamp. **Fully separable from camera and pointer-lock**: it reads only `FrameInput.keys` + `player.yaw/pitch` and mutates `player.position/velocity`. The camera boom, pointer-lock, and mouse sensitivity all live in the render/input layers, never here.
- **Aim is implicit:** `attack` and `placeBlock` resolve against `player.yaw/pitch` at execution time (raycast from the eye) — the commands carry **no target coordinates**. For an authoritative server this is actually ideal (server raycasts against its own authoritative world), but it requires each player's `yaw/pitch` to be current before the command runs — i.e. `applyLook` deltas must be networked alongside commands.

## 6. Entities / mobs

- **16 mob kinds** (`MobKind`, `types.ts:89`): sheep, chicken, horse, cow, pig, wolf, cat, cod, salmon, zombie, skeleton, spider, creeper, raider, villager, boss.
- Simulated as a **flat `state.mobs: MobState[]`** (`state.ts:29`, no three.js objects — visuals reconciled by id in the renderer). Projectiles, thrown spears, vehicles, primed TNT are parallel entity lists/maps.
- **AI** (`systems/mobAI.ts`): wander/aggro/flee, line-of-sight melee, ranged kiting (skeletons/boss), daylight burn, a faction enmity table (wild/hostile/ally/villager/raider), pet following, boss summon/spread. Movement is surface-following via `surfaceYAt`; no A* pathfinding.
- **Spawning** (`systems/spawnDirector.ts`): interval-based night hostile director, aquatic director, dungeon-spawner director, all gated by difficulty and a shared `HOSTILE_CAP`, spawning **near the player**.
- **Determinism:** mob AI, spawns, breeding, and loot all consume the injected `deps.rng` (`mobAI.ts:211-342`, `GameEngine.ts:1028-1036`) — deterministic given a seeded rng, otherwise `Math.random`. Mobs are **session-only / partially persisted** (tamed pets + villagers persist via save v14/v15; wild mobs are re-seeded each boot).
- **Single-target assumption:** mob AI, spawn distances, and random ticks all key on the singular `state.player`. This is the core multiplayer refactor (see §Hardest).

## 7. Existing seams multiplayer can hook into

This codebase has unusually clean seams — several map almost 1:1 onto netcode:

1. **Command pattern** (`commands.ts`, `GameEngine.dispatch`): "every state mutation triggered by the UI or input controller goes through `GameEngine.dispatch` with one of these — the single auditable entry point into the simulation." This is your **client→server RPC channel**. Commands are small, near-JSON-serializable discriminated unions. `applyLook(dYaw,dPitch)` is the one out-of-band input (mouse deltas) — fold it into a command or a per-tick input packet.
2. **Event bus** (`GameEngine.emit` / `consumeEvents()` returning `GameEvent[]`, `state.ts:388-448`): ~60 one-shot event types, most already carrying coordinates (`blockPlaced`, `blockBroken`, `mobDied`, `mobSpawned`, `arrowHit`, `explosion`, `bossDefeated`…). This is your **server→client broadcast stream** — the renderer and audio already consume it exactly this way, so clients would too.
3. **`blockChanges` delta tracker** (`blockChanges.ts`): tracked edits against the worldgen baseline, with reverted edits dropping out. Combined with deterministic seed-based worldgen, a joining client syncs with `{seed, worldType, blockDiff}` instead of 37 MB — **the world-state replication seam already exists** (it's the save format).
4. **Snapshot / `useSyncExternalStore`** (`buildSnapshot`, `subscribe`, `getSnapshot`): a ref-stable immutable projection rebuilt only on visible change. This is a ready-made **per-client state-delta projector** (today it's HUD-shaped and single-player; you'd add per-player projections).
5. **Injectable everything:** `rng`, `worldSize`, and `save`'s `Storage` are all constructor/param injectable (`GameEngineOptions`, `save.ts:227`). Deterministic seeded rng + server storage drop in with no code change.
6. **`GameApi` facade** (`state.ts:322`): `{ dispatch, serialize, advancementState }` — a clean, narrow interface the transport can wrap.

**There is no existing networking code, multiplayer stub, or peer/socket abstraction anywhere** (grep for websocket/socket/webrtc/peer/multiplayer/netcode = 0 hits). But the command+event+delta architecture means you'd be adding transport around an already-clean core, not surgically decoupling one.

## Top 5 hardest coupling points for headless extraction

Ranked by real effort. Note: browser decoupling is *not* in the top 5 — it's already done.

1. **Single-player state shape (by far the biggest).** `GameState` has one `player`, one `inventory`, one `hearts/hunger/oxygen/xp/effects`, one `mining` target, one `fishing`, one `mountedVehicleId`, one `openContainerIndex` (`state.ts:182-276`). Mob AI, spawn directors, random ticks, and weather all reference the singular `state.player`. Multiplayer requires a `players: Map&lt;id, PlayerState+inventory+stats+mining+…&gt;` and rewriting every system that reads `state.player` to loop over players (proximity spawning, "nearest player" aggro, per-player interest). This is a structural refactor of the whole `systems/` layer and the save format.

2. **Whole-world in-memory arrays, no chunking.** 37 MB blocks + 37 MB light baked at boot (`GameEngine.ts:185-201`), fixed 512³-ish. Fine for one browser tab; heavy for a server hosting many concurrent worlds, and there's no chunk granularity for per-client interest management or partial network sync. You'd want chunked storage + streaming, which touches `voxelWorld`, `lighting` (currently a whole-field bake/flood), and `meshing`.

3. **Determinism default is `Math.random`.** The `rng` seam exists, but for server-authoritative fairness (or lockstep) you must inject a single seeded PRNG stream and audit that *every* nondeterministic call routes through it. Spot-checked calls do (`mobAI`, `spawnDirector`, loot, `dispatch` rotten-flesh roll `GameEngine.ts:539`), but this needs a full sweep. Also `manifest.ts` id-gen and `worlds.ts` seed resolution use `Math.random` directly.

4. **Implicit-aim commands need synced look state.** `attack`/`placeBlock` raycast from `player.yaw/pitch` with no target coords (`GameEngine.ts:648-671`, `dispatch placeBlock:625`). The server must apply each client's latest `applyLook` before executing that client's action command, and reconcile ordering — straightforward but a protocol design point, and it means `applyLook` (currently a direct mutator, not a Command) should become part of the networked input.

5. **`three` dependency in the sim + input key-code coupling.** Minor but real: the engine imports `import * as THREE from "three"` for `Vector3` only. Three.js loads in Node, so it *works*, but you're pulling a large GPU library into a server process — worth replacing with a tiny `Vector3` for footprint. Separately, `FrameInput.keys` uses raw browser key codes (`"KeyW"`); the server input packet should carry an abstract movement intent (`forward/strafe/jump/crouch/sprint` booleans) rather than DOM `event.code` strings, and `playerMotion.ts:77-80` decodes them.

---

## Verdict

Extracting a headless core to run `step(dt)` on a Bun/Node server is **a few hours** of mechanical work (import `GameEngine` + `lib/world` sans `meshing`/`atlas` + `lib/game` rules, inject a seeded rng and a server `Storage`, drive `step` from a timer, wire `dispatch`/`consumeEvents` to a socket). ## Phase 1 — Deterministic foundations (worldgen portability, TickDriver, input intents)

**Goal.** Remove every cross-engine nondeterminism from the sim path and every DOM-ism from the engine's input surface, so the identical engine source can run on Bun (server) and Chromium (client) and produce byte-identical worlds and compatible behavior. No networking.

### 1a. Bit-portable worldgen (prerequisite, constraint 7)

The offenders in `lib/world/generation.ts`:
- `hash2D` (line 136): `Math.sin(x*127.1 + z*311.7) * 43758.5453123` — engine-defined.
- `smoothNoise2D` (lines 142–148): four `Math.sin`/`Math.cos` waves — engine-defined.
- `carveCaves` random-walk (lines ~290–291): `Math.sin(yaw)`, `Math.sin(pitch)` on arbitrary floats.
- Audit pass for any other transcendental in sim-affecting paths: `grep -nE 'Math\.(sin|cos|tan|atan|exp|pow|log)' lib/world lib/game/engine lib/game/spawn.ts lib/game/engine/systems/dayNight.ts lib/game/engine/systems/weather.ts`. Known additional hits: `daylightAt` (dayNight) and `weather.ts` if they use trig — both derived per-tick from `dayClock`, so make them portable too (daylight gates hostile spawn/burn on the server; weather is cosmetic but free to fix with the same helper). `playerMotion.ts` trig (`forwardFromYaw`, `lookDirection`) is fine to leave: it only affects the local frame's motion, never seed-determined bytes — but note it in docs.

New file **`lib/world/noise.ts`**:
- `hashU32(x: number): number` — integer avalanche hash (`Math.imul`, xor-shift; only int32 ops).
- `hash2D(x: number, z: number, seed: number): number` → [0,1) via integer hash of `(x|0, z|0, seed|0)` divided by 2^32. IEEE-754 add/sub/mul/div are correctly rounded per ECMA-262, so this is bit-identical everywhere.
- `valueNoise2D(x: number, z: number, seed: number): number` — integer-lattice value noise: `Math.floor` to cell, `hash2D` at 4 corners, smoothstep (polynomial, portable) bilinear blend. Compose 3–4 octaves in `smoothNoise2D`'s replacement, tuned so output range/frequency approximates the old `[-6.3, 6.3]`-ish band (the structural probes in `generation.test.ts` — flat is level, amplified higher-relief, islands flood with dry spawn, villages find flat land — are the acceptance tests for "close enough").
- `portableSin(x)/portableCos(x)` — range-reduce with `Math.floor` then a fixed minimax polynomial (only +,*, portable). Used by `carveCaves`' walk and `daylightAt`. Unit-test max error &lt; 1e-3 (plenty for cave direction and a 0.04–1.0 daylight curve).

Changes: `generation.ts` swaps to `noise.ts` imports; **`lib/game/config.ts` `WORLDGEN_VERSION` 10 → 11**; re-baseline all SHA-256 digests in `lib/world/generation.test.ts` per the documented policy (deliberate worldgen change, case 1). Move the digest constants into a new **`lib/world/generationBaselines.ts`** (exported `Record&lt;worldKey, sha256&gt;`) consumed by both `generation.test.ts` and the new e2e.

**Cross-engine determinism e2e** — new `e2e/determinism.e2e.ts`: boot the seeded fixture world, then in-page compute `crypto.subtle.digest("SHA-256", window.__monecraft.engine.state.world.blocks)` and compare against the imported baseline (test file imports `generationBaselines.ts` at Node level and passes the expected hex into `page.evaluate`). This proves Chromium ≡ Bun for the pinned seed. Also relax the CI comment: the Bun pin is no longer load-bearing for worldgen (keep the pin anyway for reproducibility).

### 1b. TickDriver extraction

Decision (within the stated latitude "engine or a shared TickDriver"): **the SP client keeps its current variable-dt rAF stepping — feel-identical, e2e-identical — and the fixed 20 Hz tick is the server's driver.** The engine is already dt-agnostic; forcing SP to 20 Hz would add ~25 ms input latency and 20 Hz position chop with no benefit until client prediction exists (explicitly out of v1).

New **`lib/game/engine/tickDriver.ts`**:
- `MAX_STEP_SECONDS = 0.05`, `MAX_SUBSTEPS = 5`, `TICK_SECONDS = 0.05`, `TICK_RATE = 20` (constants move here from `useMinecraftGame.ts:294-305`).
- `createAccumulator({ maxStepSeconds, maxSubsteps })` → `{ advance(nowMs, step: (dt) =&gt; void): number }` — the exact catch-up logic lifted from the hook (returns frameSeconds for `audio.sync`).
- `createFixedTicker({ tickSeconds, now, setTimeout, onTick })` — drift-corrected chained `setTimeout` (schedules against an absolute next-tick target, not a naive `setInterval`), used only by the server in phase 4. Pure/injectable so it's unit-testable with a fake clock.
- `useMinecraftGame.ts` swaps its inline loop for `createAccumulator`. Behavior byte-identical; add a unit test for the accumulator (slow-frame catch-up, drop-beyond-cap).

### 1c. Input intents (DOM key codes out of the engine)

`lib/game/engine/state.ts`: replace `FrameInput` with:

```ts
export type MoveIntents = { forward: boolean; back: boolean; left: boolean; right: boolean;
                            jump: boolean; sprint: boolean; crouch: boolean };
export type FrameInput = { move: MoveIntents; mineHeld: boolean };
export const IDLE_INPUT: FrameInput = { move: {...all false}, mineHeld: false };
```

- `systems/playerMotion.ts:77-91`: `keys.has("KeyW")` → `input.move.forward`, etc.; `sprinting = move.sprint &amp;&amp; forwardInput &gt; 0 &amp;&amp; !crouching` (CapsLock resolution moves into the input controller).
- `capsActive` leaves the engine: `inputController` owns it; the HUD caps indicator reads a new `sprintHeld` React state exposed by the hook from the controller (snapshot field `capsActive` renamed `sprintActive`, fed from `input.move.sprint` in `step` — smallest-diff option; either is fine, pick one and update `StatusBars`/HUD test).
- `pointerLocked` leaves the engine: `inputController` only reports `mineHeld = leftMouseHeld &amp;&amp; pointerLocked` (audit `systems/mining.ts` for `input.pointerLocked`/`leftMouseHeld` reads).
- `applyLook(dYaw, dPitch)` stays as the local-look mutator (client-authoritative in MP too); no change yet.
- `inputController.ts` becomes the single DOM→intent mapper (future keybinding config lands here for free).

**Tests:** update `playerMotion`/`GameEngine`/`inputController` tests to build `FrameInput` via a small `intents({forward:true,...})` helper (add to a shared test util so 40+ call sites are one-line changes). **Docs:** `architecture.md` (input section, TickDriver), `testing.md` (worldgen policy update: cross-engine determinism now guaranteed and e2e-pinned; re-baseline recorded), `save-format.md` (WORLDGEN_VERSION 11 entry — old worlds discard diffs and reboot from seed), CHANGELOG.

**Risks:** value-noise terrain diverges enough to fail structural probes (mitigate: tune octave amplitudes until probes pass; probes, not hashes, define acceptance); a missed transcendental somewhere in the seed-determined path (mitigate: the grep audit + the cross-engine e2e catches it); users lose block edits on the v11 re-roll (accepted per policy; flag in CHANGELOG).

**Verification:** full gate + `bun run test:e2e` (all existing + new determinism spec). Manual: play a world, confirm terrain still looks sane in all four world types.

## Phase 2 — Multi-player engine core (players map, save v17)

**Goal.** `GameState.player` → `GameState.players: Map&lt;PlayerId, PlayerState&gt;` with every per-avatar concern moved inside, all 23 systems converted, per-player command attribution — while SP behavior and the existing e2e suite stay bit-for-bit compatible.

### State shape (`lib/game/engine/state.ts`)

```ts
export type PlayerId = string;                 // "local" in SP; userId in MP
export const LOCAL_PLAYER_ID: PlayerId = "local";

export type PlayerState = {
  id: PlayerId; name: string; skinId: SkinId;
  position: THREE.Vector3; velocity: THREE.Vector3;
  yaw: number; pitch: number; onGround: boolean;
  gameMode: GameMode; isFlying: boolean;
  inventory: InventorySlot[]; equippedArmor: EquippedArmor; selectedSlot: number;
  hearts: number; hunger: number; oxygen: number;
  effects: Map&lt;EffectId, number&gt;; xp: number;
  stats: Map&lt;string, number&gt;; advancements: Set&lt;string&gt;;
  isDead: boolean; respawnTimer: number; gameOver: boolean;   // per-player permadeath in MP
  sleeping: boolean;                                          // in-bed flag (see sleep below)
  spawnPoint: {x,y,z} | null;
  mining: MiningState; fishing: FishingState | null;
  mountedVehicleId: number | null;
  inventoryOpen: boolean; advancementsOpen: boolean;
  craftingStation: ...; activeVillagerProfession: ...; openContainerIndex: number | null;
  input: FrameInput;                                          // latest intents (set per frame/packet)
  timers: PlayerTimers;                                       // split of GameTimers, below
};
```

`GameTimers` splits: **PlayerTimers** = void/regen/waterExposure/waterDamage/lavaBurn/lavaDamage/drown/starvation/sprint-walk-jump budgets/effectRegen/effectPoison/stuck/spearThrowCooldown/bowCooldown. **WorldTimers** (stay on `GameState.timers`) = hostileSpawn/aquaticSpawn/spawner/randomTick/breed. `daylightHudTimer`/`debugHudTimer` are presentation → keep on world timers (harmless) or move next to snapshot code.

`GameState` gains `players: Map&lt;PlayerId, PlayerState&gt;` and `primaryPlayerId: PlayerId`, and **keeps `player`, `inventory`, `hearts`, `hunger`, `xp`, `effects`, `stats`, `advancements`, `selectedSlot`, `equippedArmor`, `isDead`, `mining`, `fishing`, `mountedVehicleId`, `openContainerIndex`, `spawnPoint`, `gameMode`, `isFlying`, `inventoryOpen`, `oxygen` as accessor properties delegating to `players.get(primaryPlayerId)`** (defined once via `Object.defineProperties` in a new `lib/game/engine/players.ts` `createGameStatePlayerAliases(state)`). This is deliberate and permanent, not transitional: it keeps `window.__monecraft.engine.state.player.position` and every existing e2e assertion (`e2e/helpers.ts:74`, `smoke.e2e.ts` mutating `state.player.yaw`) working, and keeps SP call sites readable. Systems, however, are converted to explicit player params — the aliases are for the shell/tests/console only. Document the invariant: *engine systems must never read the aliases.*

`MobState.owner?: "player"` → `owner?: PlayerId`; `VehicleState.rider: "player" | null` → `rider: PlayerId | null` (save v17 migrates `"player"` → the wrapped player's id).

### Engine surface (`lib/game/engine/GameEngine.ts`)

- `dispatch(command: Command, playerId: PlayerId = state.primaryPlayerId)` — every `state.inventory`/`state.hearts`/... read in the big switch becomes `p = mustGetPlayer(state, playerId)`. `GameApi` unchanged for the UI; engine adds `apiFor(playerId): GameApi` (SP uses `apiFor(LOCAL_PLAYER_ID)`, which is what `buildSnapshot` publishes).
- `step(dt: number)` — input moves off the signature: `setPlayerInput(playerId, input: FrameInput)` stores into `PlayerState.input`; the hook calls it right before `step`. Per-step loop: for each player → stuck check, death/respawn tick, motion (`tickPlayerMotion(state, p, dt, ...)`), stats/hazards/status effects, mining, fishing, look-derived systems; then world systems once (dayNight, weather, randomTicks, spawn directors, mobs, TNT, projectiles, breeding, raid, vehicles).
- `emit` gains attribution where the shell/audio needs it: `GameEvent` gets an optional `playerId` on player-scoped events (`died`, `respawned`, `playerHurt`, `ateFood`, `jumped`, `landed`, `attackSwung`, `xpGained`, `advancementUnlocked`, fishing/sleep/anvil/enchant events…). SP shell filters/ignores it. `observeProgress` folds into the *acting player's* stats.
- `applyDamage`/`applyEnvironmentalDamage`/`applyPoisonDamage` become curried per player: `applyDamageTo(playerId)(amount)`; `mobTickDeps` carries `players` + `applyDamageTo`.
- Snapshot: `buildSnapshot()` projects the **primary** player (unchanged fields); MP viewers each run their own client engine so per-viewer projection on one engine is only needed server-side — and the server never builds snapshots: add `GameEngineOptions.headless?: boolean` that skips `refreshSnapshot` entirely (also a small perf win; the server drains events instead).
- `addPlayer(spec: {id, name, skinId, restore?: SavedPlayer}): PlayerState` / `removePlayer(id): SavedPlayer` (serialize-on-leave). Fresh players spawn via `findSpawnOnLand`.

### System-by-system

- **`systems/mobAI.ts`** — `nearestTargetablePlayer(state, mob)` replaces the singular reads at lines 153–160, 176–178, 250, 279–342, 411, 430: filter `!isDead &amp;&amp; mobsThreaten(p.gameMode)`, pick nearest by XZ distance; aggro/kiting/boss spread/knockback (`playerVelocity` write at :430) all use the chosen target. Fish flee the nearest player. `creditPlayer` for pet kills = pet's `owner`.
- **`systems/spawnDirector.ts`** — `spawnInitialMobs` centers on world spawn (unchanged); night director loops players (`tickHostileSpawnDirector`): each interval pick a random player as spawn center (round-robin), global `HOSTILE_CAP × hostileCapScale × ceil(players/2)` cap so 8 players don't get 8× mobs but also don't starve; aquatic director likewise. Spawner activation (:250): *any* player within `SPAWNER_ACTIVATION_RADIUS`.
- **`systems/randomTicks.ts`** — sample columns around each player, per-player budget = `RANDOM_TICK_SAMPLES / players.size` (bounded below), so total work is constant.
- **Sleep** — per-player `sleeping` set by bed interaction (`systems/interact.ts`); when **every non-dead, non-spectator player** sleeps, the existing global `sleepTimer` fade engages and `wakeToMorning()` clears all `sleeping` flags. SP: one player ⇒ identical observable behavior (same code path). A sleeping player is immobilized (motion skipped) and can `wake` (new Command `{type:"wakeUp"}` dispatched by moving/Esc) — needed so one AFK-in-bed player doesn't hold the fade hostage; in SP the instant-fade means this is unreachable, preserving behavior.
- **Pause** — `GameEngineOptions.authority: "local" | "server"` (default `"local"`). `dispatch("pause")` sets `state.paused` only under `"local"`; under `"server"` it's ignored (personal menus don't freeze the world — that's a client/UI concern in phase 5). The step-0 pause gate is unchanged for SP.
- **Death/respawn** — `tickRespawnTimer`/`respawn()` per player; while a player is dead only *their* per-player systems skip; the world keeps ticking (SP-visible difference: in SP today "only mobs tick while dead" — keep the SP semantics by gating world systems on `authority === "local" &amp;&amp; primary.isDead` to preserve the existing e2e/death behavior exactly; on the server everything always ticks).
- **Hardcore in MP** — per-player permadeath: death flips that player to spectator with `gameOver=true`; world-level `gameOver` (the existing flag) = all players gameOver (drives SP boot-into-spectator unchanged).
- **`systems/interact.ts`, `mining.ts`, `combat.ts`, `fishing.ts`, `spears.ts`, `vehicles.ts`, `projectileAI.ts`** — take `player: PlayerState` explicitly; raycasts read that player's yaw/pitch/eye. `ProjectileState.fromPlayer: boolean` → `ownerPlayerId: PlayerId | null` (hit filter: player arrows hit mobs, mob arrows hit any player, nobody hits the firer).
- **`systems/weather.ts`** — biome read uses the primary player locally; under `authority:"server"` skip (cosmetic, derived client-side from replicated `dayClock` + seed — free because it's a pure function).

### Save v17 (`lib/game/types.ts`, `lib/game/save.ts`)

`SaveDataV17 = Omit&lt;SaveDataV16, playerFields&gt; &amp; { version: 17; players: SavedPlayer[] }` where `SavedPlayer` = `{ id, name?, skinId?, position, inventorySlots, equippedArmor, selectedSlot, hearts, hunger, effects, xp, stats, advancements, spawnPoint, gameMode, gameOver }`. World-level fields stay top-level: seed, worldType, difficulty, hardcore, changes, blockEntities, lootedChests, mobs, vehicles, dayClock, villagesSeeded. `migrateSaveV16toV17` wraps the flat single-player fields into `players: [{ id: "local", ... }]` and rewrites mob `owner:"player"`/vehicle rider drops. `serialize()` emits v17; `readSave` chains …v16→v17. Round-trip + migration tests in `save.test.ts`; docs/save-format.md gets the v17 entry.

**Docs:** rewrite `architecture.md` engine section (players map, authority, aliases invariant); `save-format.md` v17; `testing.md` (multi-player test helper: `addTestPlayer(engine, id)`); CHANGELOG. **New tests:** a `GameEngine.multiplayer.test.ts` — two players, mob targets nearer one, per-player death doesn't kill the other's session, per-player inventory isolation, all-asleep skips night, save round-trips two players.

**Risks (biggest of the project):** ~13.4k LOC blast radius. Mitigations: the alias layer keeps shell/e2e compiling from day one; convert systems in dependency order (playerStats/playerLife → motion → mining/combat/interact → mobAI/spawnDirector → the rest), each with its tests green before the next; forbid alias use inside `lib/game/engine/systems/` with a lint restriction (`no-restricted-syntax` on `state.player` within that dir) once conversion completes.

**Verification:** full gate; **all existing e2e pass unchanged** (this is the phase's acceptance bar); new MP engine tests.

## Phase 4 — Game server + protocol (Fly side)

**Goal.** A single Bun process hosting N rooms, each an authoritative `GameEngine`, speaking protocol v1 over WebSocket, persisting to Postgres. Fully testable headlessly.

### Shared protocol — `lib/net/` (client + server both import via `@/`)

- `lib/net/protocol.ts` — `export const PROTOCOL_VERSION = 1;` message unions + total validators (hand-rolled, `save.ts` house style — no zod dep needed):

**C2S:** `hello {ticket, protocol}` · `pose {seq, x,y,z, yaw,pitch, onGround, tick}` (20 Hz) · `cmd {seq, cmd: Command, pose: {x,y,z,yaw,pitch}}` (pose = client-claimed eye pose at click time; server applies it — sanity-checked — before dispatch, so aimed raycasts resolve server-side without changing `Command` shapes) · `chat {text}` · `ping {id, tMs}` · `resync {}`

**S2C:** `welcome {protocol, playerId, worldId, seed, worldType, gameMode, difficulty, hardcore, dayClock, tick, players: [{id,name,skinId,x,y,z,yaw}]}` · **world sync** (one binary frame: gzipped JSON `WorldSync {changes, blockEntities, lootedChests, mobs, vehicles, containersOpenable, dayClock, tick}` — join payload per constraint 1) · `tick {n, ev: AttributedGameEvent[], pp: [id,x,y,z,yaw,pitch,flags][], mp: [mobId,x,y,z,yaw,hp][] /* deadband: only mobs that moved &gt; 0.05 or hp changed; 10 Hz (every 2nd tick) */, day?: dayClock /* every 20 ticks */, self?: SelfDelta}` · `mobsKeyframe {full list}` (every ~5 s, drift correction) · `playerJoined {id,name,skinId}` / `playerLeft {id,reason}` · `container {index, slots}` (to players with it open) · `chat {from,name,text}` · `pong {id, tMs, serverTick}` · `forcePose {x,y,z,yaw,pitch}` (position-sanity correction) · `kick {code, reason}`.

`SelfDelta` (private, per client, only-when-changed): `{inv?, armor?, selectedSlot?, hearts?, hunger?, oxygen?, xp?, effects?, stats‑digest?, advancements?, isDead?, respawnSeconds?, sleeping?}` — the server-authoritative mirror of everything the SP snapshot shows.

**Close codes:** 4000 bad ticket · 4001 protocol mismatch · 4002 room full (&gt;8) · 4003 kicked · 4004 idle timeout · 4005 server shutdown · 4008 slow client/backpressure.

Binary path: v1 is JSON (`pose`/`tick` included) except the gzipped world-sync frame; the envelope discriminant `t` and versioned `hello` leave room to move `pose`/`tick.pp/mp` to packed ArrayBuffers later without renegotiating anything else.

- `lib/net/codec.ts` — encode/decode + gzip (`Bun.gzipSync` server / `DecompressionStream` client). `lib/net/clock.ts` — RTT/serverTick estimator (EWMA over pings every 2 s).

### Server — `server/`

**Room lifecycle (`room.ts`):**
- Construct: `new GameEngine({ save: parsedBlob ?? null, seed, worldType, difficulty, hardcore, authority: "server", headless: true })`; `createFixedTicker(TICK_SECONDS)` drives `step`.
- Per tick: apply queued pose packets through **`applyRemotePoses(state, player, samples)`** — the server-side replacement for `tickPlayerMotion` (skipped under `authority:"server"`): clamp horizontal speed to `SPRINT_SPEED × maxSpeedEffect × 1.25`, vertical to terminal velocity, reject &gt;10-block jumps (snap back + `forcePose`), derive `onGround`/landing vy from sample deltas and feed a synthesized `MoveTickResult` into the unchanged hunger/stat/fall-damage pipeline; then `engine.step(dt)`; then drain `consumeEvents()` → attribute → broadcast `tick` (with per-client `self` deltas computed by diffing each player's server state against the last-sent shadow).

- Chat: rate-limit 3 msg/s, 256 chars, broadcast; not an engine concern.

## Riskiest assumptions (flagged)

1. **IEEE-754 cross-engine determinism of the sim** beyond worldgen: v1 only *requires* worldgen bytes to match (server is authoritative for everything else; client motion is client-authoritative), so this is contained — but if later phases assume replica physics ≡ server physics, transcendentals in `playerMotion` become relevant. Documented, not needed for v1.
2. **Phase 2 blast radius** — the players-map refactor touches nearly every system and test. The alias layer + system-by-system conversion + "existing e2e must pass" bar is the containment strategy, but this phase will dominate the schedule.
3. **better-auth anonymous→upgrade data re-parenting** — the whole "guest keeps worlds" promise hangs on one plugin hook; integration-test it first, before building UI on top.
4. **Single-threaded Bun room budget** — 6–10 engines × ≤50 ms ticks on one core is *probably* fine (SP steps at 60 fps in a browser next to rendering) but must be measured before raising `MAX_ROOMS`; the fallback (multiple Fly machines with room→machine affinity via the ticket mint) does not change the protocol.
5. **Value-noise terrain quality** — probes pin structure, not beauty; budget a tuning loop.

## Where I'd push back (briefly, not relitigating)

- **Client-claimed pose on command envelopes** is the weakest anti-cheat point of the hybrid model (a modified client can aim-bot/reach-hack). Acceptable for private invite-only co-op; the envelope shape is exactly what server-side rewind validation would consume later, so nothing is wasted.
- **`kind: 'sp-cloud' | 'mp'` as disjoint world kinds** invites future "convert my SP world to online" requests; the schema (one `saveBlob`, same v17 format) already permits a one-way kind flip — recommend explicitly allowing owner-initiated SP→MP conversion in v1.5 rather than designing it out.
