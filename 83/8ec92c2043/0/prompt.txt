# Redstone-lite feasibility report — block representation &amp; rendering

All paths absolute; line references verified against current source.

## 1. BlockId space

**File:** `/Users/hutusi/workspace/ai/david/monecraft/lib/world/blocks.ts`

- `BlockId` is a `const enum` (blocks.ts:5-87). Highest id in use is `CoralBlue = 57`, so **58 ids used (0–57)**. World stores blocks in a `Uint8Array` (`voxelWorld.ts:32`, `new Uint8Array(sizeX*sizeY*sizeZ)`), value range 0–255, so **~198 ids free; next free id is 58**.
- **Append-only convention** is explicit and load-bearing: docs say append new ids "at the end of the enum so saved ids don't shift" (`docs/adding-content.md:99`). Save deltas are `[voxelIndex, blockId]` pairs (`blockChanges.ts:13,67`), so renumbering corrupts every save.
- **State-variant ids — the 16 door blocks 30–45.** They encode **3 axes = facing × open × half**, NOT hinge:
  - facing (4): north/east/south/west
  - open (2): closed / open
  - half (2): lower / upper
  - 4 × 2 × 2 = 16. There is **no hinge bit** (Minecraft's left/right hinge is not modeled).
- **Offset math** (`doors.ts:26-48`): `DOOR_FIRST = DoorNorthLower = 30`. Layout is `open*8 + facingIndex*2 + upper`.
  - `doorState(block)` (doors.ts:35-43): `index = block - 30`; `facing = FACING_ORDER[floor((index % 8) / 2)]`; `open = index &gt;= 8`; `upper = index % 2 === 1`.
  - `doorBlock(facing, open, upper)` (doors.ts:45-48): `30 + (open?8:0) + facingIndex*2 + (upper?1:0)`.
  - `isDoorBlock` is a simple range check `30..45` (doors.ts:31-33).
- Other consecutive-id "state" runs (advance by +1): **WheatStage0–3 = 22–25** (blocks.ts:28-32; grown via `block+1` in randomTicks.ts:26-30). These are the model for a redstone-wire-power-level encoding if you go the "N consecutive ids" route.
- Two color tables you must extend for any new block: `BLOCK_COLORS` (float RGB, feeds the atlas — blocks.ts:138-206) and `HELD_BLOCK_COLORS` (held-item tint — blocks.ts:99-132).

## 2. Non-cube rendering precedent

**File:** `/Users/hutusi/workspace/ai/david/monecraft/lib/world/meshing.ts`

- **Doors are the ONLY non-full-cube block today.** The mesher expresses them via `pushBlockCuboid` with per-block X/Z bounds:
  - Main loop branch: `if (isDoorBlock(block)) { const bounds = doorBounds(block)!; pushBlockCuboid(target, block, x, y, z, bounds.minX, bounds.maxX, bounds.minZ, bounds.maxZ); continue; }` (meshing.ts:242-246).
  - `pushBlockCuboid` (meshing.ts:217-234) emits all 6 faces of an inset box. **Critically, it insets only X and Z — Y is hardcoded full-height** (`y + cy`, where cy ∈ {0,1}, meshing.ts:225). There is no minY/maxY support today.
  - `doorBounds` (doors.ts:58-70) returns a 3/16-thick panel (`THICKNESS = 3/16`, doors.ts:29), positioned at the mid-face when closed, rotated onto the hinge edge when open. So a door is a **thin full-height box, not a full cube with transparent texture**.
  - Door faces don't cull neighbors and aren't culled by neighbors: face-culling special-cases `!isDoorBlock(neighbor)` (meshing.ts:254), and doors never enter the normal per-face loop (they `continue` at 246).
- **Torches render as FULL CUBES.** There is no special mesh branch for `Torch`; they fall through to the standard 6-face cube path (meshing.ts:247-275). Their "torch look" is entirely painted in the atlas (a stick + flame on a dark ground — atlas.ts:121-131) plus their block-light glow.
- **Non-full-cube geometry seam:** there is a per-block **cuboid** seam (`pushBlockCuboid`) but it is X/Z-inset only. To render:
  - **A flat wire overlay on top of a block** — you'd add a branch like the door branch calling a cuboid helper, but you must **extend `pushBlockCuboid` to accept minY/maxY** (currently full-height). No per-face geometry/UV system and no multi-piece models exist; every cuboid face samples one tile via `tileIndexFor(block, face)` (meshing.ts:183-195, atlas.ts:30-33).
  - **A small lever handle** — same story: needs a Y-bounded cuboid (a second small box) and, if you want the base + handle to differ, either two blocks or a second draw. No composite-geometry infrastructure exists.
  - Per-face texture variation exists only at the top/side/bottom granularity (see §3), so a "wire crossing on top, plain on sides" texture is expressible, but arbitrary per-face-direction (N vs S) tiles are not.

## 3. Block textures

**File:** `/Users/hutusi/workspace/ai/david/monecraft/lib/world/atlas.ts`

- Procedural 16×16-per-tile atlas painted on a canvas at startup (`createBlockAtlasTexture`, atlas.ts:35-225). **The only world module that touches the DOM.**
- **Per-face variation = 3 variants: top / side / bottom** (`ATLAS_FACE_VARIANTS = 3`, atlas.ts:8; `tileIndexFor(block, face) = block*3 + faceId`, atlas.ts:30-33). The mesher chooses `top` for ny&gt;0, `bottom` for ny&lt;0, else `side` (meshing.ts:183-186). Example of top/side/bottom variation: grass side gets a green fringe and grass bottom is painted as dirt (atlas.ts:58,66).
- **Pattern to add a block's pixels:** the atlas auto-sizes from `BLOCK_COLORS` (`ATLAS_BLOCK_COUNT = max(BLOCK_COLORS keys)+1`, atlas.ts:13; rows derived at atlas.ts:14). So step 1 is a `BLOCK_COLORS` entry (blocks.ts:138) — **without it the block indexes past the atlas and samples garbage UVs** (the fix is documented in the atlas.ts:11-13 comment). Then add an `if (block === BlockId.X) { … }` paint branch inside `drawTile`'s pixel loop (atlas.ts:60-202); every existing block does this (e.g. Torch atlas.ts:121-131, TNT 111-120, doors 193-202). The draw loop runs for every block `Grass..ATLAS_BLOCK_COUNT` (atlas.ts:210-214).
- **Emissive / glow look:** there is **no emissive material flag on the atlas or block**. Torches/lava "glow" through two independent mechanisms:
  1. They emit **block light** (see §4), which the world shader adds back as an albedo-tinted glow (`gl_FragColor.rgb … + mcAlbedo * vLight.y * TORCH_TINT`, `GameRenderer.ts:57`; `TORCH_TINT = vec3(1.35,1.06,0.62)`, GameRenderer.ts:36). This is what actually makes them read as light sources.
  2. The atlas simply paints bright warm pixels (lava crust/cracks atlas.ts:104-110, torch flame atlas.ts:121-131, furnace mouth atlas.ts:88), which look lit because the block-light term brightens their own face.
  - So **a new "redstone lamp" that glows uses the exact same recipe: add `emission()` in lighting.ts + paint bright pixels.** No shader change needed.

## 4. Lighting

**File:** `/Users/hutusi/workspace/ai/david/monecraft/lib/world/lighting.ts`

- Two 4-bit channels packed per voxel: `light[idx] = (skyLight&lt;&lt;4) | blockLight` (lighting.ts:6-8; accessors voxelWorld.ts:59-69). It is a **derived cache, never serialized** (lighting.ts:16-18, `docs/save-format.md:38`).
- **Emitters are declared in `emission(block)`** (lighting.ts:73-82): `Torch → 14`, `Lava → MAX_LIGHT (15)`, default `0`. A new lamp = one `case` here.
- **Opacity** (how much light a block absorbs) is `opacity(block)` (lighting.ts:49-61): Air/Glass 0, Leaves/Water/Kelp 1, everything else `OPAQUE (15)`. A new solid lamp defaults to OPAQUE (blocks light) unless you add a case.
- **`applyEdit(world, light, x, y, z)`** (lighting.ts:128-162) patches both channels after a single edit using remove-then-refill BFS floods. For block light it: zeroes the cell, removes what it had lit, then **re-reads the new block's own `emission(block)` and reseeds it** (lighting.ts:135-143). This is the whole runtime-emission mechanism.
- **Where applyEdit runs:** it is called from exactly one chokepoint — `blockChanges.set` (`blockChanges.ts:47`, `applyEdit(world, world.light, x, y, z)`), which every gameplay edit (mining, doors, farming, explosions, crop growth) funnels through. The load path (`applySavedChanges`) bypasses it and relies on the full bake `computeFullLight` (lighting.ts:115-120, blockChanges.ts:54-65).
- **Toggling emission at runtime (torch off/on, lamp powered/unpowered):** because `applyEdit` re-derives emission from the block id at the edited cell, **the ONLY thing required is to change the block id at that voxel via `state.blockChanges.set(x,y,z,newId)`** — e.g. `TorchOff → TorchOn` as two ids with different `emission()` values. That single write relights the neighborhood (remove old flood + refill from new emission) and, with `state.worldMeshDirty = true`, remeshes. There is no in-place "mutate emission of an existing voxel without changing its id" path — the model is one-id-per-emission-level, exactly like WheatStage/door variants. So a lamp/lit-torch pair follows the door pattern: two BlockIds, swap between them.

## 5. Interaction routing

**File:** `/Users/hutusi/workspace/ai/david/monecraft/lib/game/engine/systems/interact.ts`

- Right-click and KeyE both dispatch the `placeBlock` command; the engine runs a **fixed precedence chain** in `GameEngine.dispatch` (`GameEngine.ts:910-936`), in order: throw spear → tame mob → feed mob → toggle-sit pet → trade villager → board vehicle → **`tryInteractBlock`** → summon boss → start raid → fish → place vehicle → `tryUseHeldItem` → `placeSelectedBlock`. First handler to return `true` consumes the click.
- **`tryInteractBlock`** (interact.ts:67-87): raycasts the aimed block (`voxelRaycast`, `MINE_REACH`), looks it up in `INTERACTIVE_BLOCKS` (`Partial&lt;Record&lt;BlockId, InteractiveKind&gt;&gt;`, interact.ts:33-57), and dispatches to a `kind`-specific handler. Chest vs door vs bed/furnace/brewing/etc. is a `kind` switch at interact.ts:78-86. This is the documented extension point (`docs/adding-content.md:81-83`).
- **Door open/close end-to-end** (`interactDoor`, interact.ts:89-101):
  1. Read `doorState` of the aimed cell; find the lower half (`current.upper ? y-1 : y`).
  2. Validate the lower+upper pair matches (same facing, same open state, correct halves) (interact.ts:95).
  3. `state.blockChanges.set` **both cells** to the flipped-open door id via `doorBlock(facing, !open, half)` (interact.ts:96-97) — a pure BlockId swap.
  4. `state.worldMeshDirty = true` (interact.ts:98) → renderer remeshes (GameRenderer.ts:609-631). Lighting is patched automatically by the `blockChanges.set` chokepoint.
  5. Emit `doorToggled` (interact.ts:99).
- **Where a "toggle lever" slots in:** register `BlockId.Lever → "lever"` in `INTERACTIVE_BLOCKS` (interact.ts:33), add `"lever"` to the `InteractiveKind` union (interact.ts:31), add a branch in the `tryInteractBlock` switch (interact.ts:78-86), and write a `interactLever` handler that swaps `LeverOff↔LeverOn` block ids (exactly like `interactDoor`) plus kicks off whatever power-propagation you design. Buttons/pressure plates would also live here (button) or in a per-frame system (pressure plate needs entity-proximity, not a click).
- Note: torch→TNT ignition is NOT in `INTERACTIVE_BLOCKS`; it's in `tryUseHeldItem` because it keys on the *held item* being a torch aimed at TNT (`primeTnt`, interact.ts:311-315). Redstone-item-based interactions (e.g. flint&amp;steel-style) would follow that held-item pattern instead.

## 7. Random ticks + timed block behavior

**Random ticks:** `/Users/hutusi/workspace/ai/david/monecraft/lib/game/engine/systems/randomTicks.ts`

- `tickRandomBlocks` (randomTicks.ts:94-118): every `RANDOM_TICK_INTERVAL_SECONDS` it samples `RANDOM_TICK_SAMPLES` columns within `RANDOM_TICK_RADIUS` of each player and runs `RANDOM_TICK_HANDLERS[topBlock]` on the column's **top block only** (`highestSolidY`, randomTicks.ts:113-115). Split across players for constant cost (randomTicks.ts:104-106).
- Handler registry `RANDOM_TICK_HANDLERS: Partial&lt;Record&lt;BlockId, handler&gt;&gt;` (randomTicks.ts:84-92): WheatStage0-2 → `growCrop` (+1 id, randomTicks.ts:26-31), Sapling → `growSapling` (checks soil below, randomTicks.ts:34-39), Dirt → `spreadGrass` (reads 4 neighbor column tops, randomTicks.ts:48-59), Kelp → `growKelp` (randomTicks.ts:67-82). Every handler edits via `state.blockChanges.set` + `worldMeshDirty` and persists for free through the block diff.

# Implementation Plan: `feat/redstone-lite`

Player-buildable power circuits: lever, button (timed pop-back), pressure plate, redstone torch (inverter), redstone wire, and consumers (doors, TNT, a new glowing lamp). **Zero save bump (stays v17), zero worldgen bump (stays 11), zero binary assets, multiplayer rides the existing server-authoritative block-delta pipeline for free.** All verified facts from the brief re-confirmed against current source.

## 1. Design decisions (settled, with rationale)

### D1. Signal model: binary, BFS budget 15, slope-climbing wire
Binary on/off with a wire-step budget of `REDSTONE_WIRE_RANGE = 15` counted only across wire→wire hops. Gives the "wire runs out" feel with exactly **2 wire ids** instead of 16 strength variants (state-as-BlockId stays cheap). Wire connects to candidate wire neighbors at the 4 horizontal offsets **at the same Y and at ±1 Y** (8 probes/cell) — Minecraft-like slope climbing, unconditional (no "cut by block above" check; that refinement isn't worth the complexity in lite). Wire additionally *powers* all 6 face neighbors of its cell (that's how it powers a torch's support block, a door cell, a lamp, TNT).

### D2. Recompute: tracked-set + fixed-cadence full recompute + per-pass self-heal (option a)
- `state.redstone.cells: Set&lt;voxelIndex&gt;` — **session-only, never serialized**.
- **Seeded at boot** by scanning `state.blockChanges.changes()` for redstone-family ids. This is complete because every redstone block is craft-only ⇒ player-placed ⇒ present in the save diff (BrewingStand/Anvil precedent).
- **Maintained at exactly one seam**: successful placement in `placeSelectedBlock` calls `trackRedstoneCell`. No other producer needed.
- **Self-heal covers everything else**: each recompute pass iterates `cells` and drops any index whose current block is no longer a redstone id (mining, explosions, server-applied edits, any overwrite — none of them need to know redstone exists). It also pops any **overlay component whose support block vanished** (→ Air, no drop; the explosion that removed the support almost certainly vaporized the component too at blastResistance 0.4) and any **ButtonOn with no timer entry** (the post-reload heal — a save mid-press reloads pressed, first pass pops it back).
- **Fixed cadence**: an accumulator inside the redstone state runs the recompute every `REDSTONE_TICK_SECONDS = 0.1` (engine dt ≤ `MAX_STEP_SECONDS` 0.05, so at most one recompute per step). This makes the torch clock deterministic (~0.2 s period for a 1-torch loop) instead of rAF-rate-dependent, and bounds cost to 10 Hz over player-scale circuits. No dirty flag: a full pass over a few-hundred-cell set at 10 Hz is trivial, and a stable circuit **writes nothing** (writes only on state change), so no remesh/relight/net traffic when idle.

### D3. Shapes, solidity, support
Six "overlay" (non-cube, non-colliding) ids — wire, lever×2, button×2, plate×2, torch×2 — plus the lamp as a plain full cube. Handling per function:

| Seam | Change |
|---|---|
| `lib/world/meshing.ts` `pushBlockCuboid` (:217) | add `minY`/`maxY` params (door call site passes `0, 1`) |
| `lib/world/meshing.ts` block loop (:242) | `isRedstoneOverlay(block)` branch → `pushBlockCuboid` with `redstoneBounds(block)`; **no** neighbor culling (door precedent) |
| `lib/world/meshing.ts` cull condition (:254) | add `&amp;&amp; !isRedstoneOverlay(neighbor)` so faces behind a wire/lever aren't culled |
| `lib/world/queries.ts` `collidesAt` (:132) | `if (isRedstoneOverlay(block)) continue;` before the door branch — components never collide; players/mobs stand on the block below, feet occupying the plate cell (exactly what plate detection needs) |
| `lib/world/voxelWorld.ts` `highestSolidY` (:71) | exempt `isRedstoneOverlay` alongside `isDoorBlock` (spawn/mob ground finding) |
| `lib/world/voxelWorld.ts` `isSolid` | **unchanged** (stays true) — keeps `voxelRaycast` able to target components for mining/interact, same trade the doors made |
| `lib/world/lighting.ts` `opacity` (:49) | overlays → `0` (a wire must not black out its cell); lamp stays default-opaque (an opaque emitter, the Lava precedent) |

Bounds (in `redstoneBounds`, doors.ts-style): wire `y 0–0.07`, full x/z with 1/16 inset; plate `y 0–0.07` off / `0–0.04` on, 1/16 inset; button `0.3–0.7` x/z, `y 0–0.15` off / `0–0.08` on (pressed reads visually — on/off are different ids so different bounds are free); lever `0.35–0.65` x/z, `y 0–0.45` (handle direction painted per on/off tile); redstone torch `0.4–0.6` x/z, `y 0–0.65`.

**Placement rule** (all overlays): target cell Air/Water AND `world.isSolid(tx, ty-1, tz)` AND below is not itself an overlay/door. Refund-and-return on failure (door-branch precedent in `placeSelectedBlock`). **Support-break cascade**: in `tickMining`, after committing a break, if the cell above held an overlay, break it too and route its drop through `addBlockDrop` to the mining player (kelp-cascade precedent, mining.ts:182-193 — there is no ground-item entity in this game, so pop-off drops must be player-attributed or nothing).

### D4. Torch inverter semantics — no self-feedback by construction
A redstone torch sits on its support block (below). Rule: **a torch powers its 6 neighbors *except* its support cell**; **a torch's next state is OFF iff its support cell is in this pass's powered set**. Because a torch never powers its own support, no exclusion hack is needed — self-oscillation within one pass is impossible. The recompute is a synchronous single-pass update (all next-states computed from the current grid, then applied), i.e. a clocked cellular update at 10 Hz: a NOT gate has one 0.1 s delay; a torch clock oscillates at 5 Hz. Sane, deterministic, tunable via `REDSTONE_TICK_SECONDS`. (Real-MC "torch burnout" hysteresis: explicitly deferred.)

### D5. Doors: edge-triggered forcing
`state.redstone.prevDoorPowered: Set&lt;lowerHalfIndex&gt;` (session-only). Rising edge (newly powered) → force both halves open via `doorBlock(facing, true, ...)` + `doorToggled` emit; falling edge → force closed. Between edges, manual `interactDoor` works untouched — matching Minecraft (you *can* hand-close a powered door; the next power *edge* reclaims it) and never fighting the player at 10 Hz. Pair consistency reuses the doors.ts pair logic exactly as `interactDoor` does (interact.ts:89-101). A door is "powered" when either of its two cells is in the powered set (wire beside the door or a source/wire on the block next to it reaches it via the 6-neighbor powering rule).

### D6. Pressure plates: players AND mobs
Both — traps are the fun. Occupancy per pass: for each player, cell `(floor(px), floor(py + 0.05), floor(pz))` (feet cell — matches the collidesAt skip: feet rest in the plate cell); for each mob, `(floor(mx), floor(my − halfHeight + 0.05), floor(mz))` (**MobState.position is body center** — state.ts:125). Cost: |players| + |mobs| lookups at 10 Hz against a small plate subset of `cells`. Plate id flips on change only.

### D7. Recipes &amp; progression (all from existing materials — worldgen deferral honored)
- **Redstone Dust**: `1 Gold Ore + 1 Coal → 8 Redstone Dust` — gold (conductor) is gated behind a tier-3 pick, coal is the powder carrier; 8/craft keeps wire affordable. *Explicit deferral note in CHANGELOG/docs: redstone ore worldgen comes with a future `WORLDGEN_VERSION` batch.*
- **Lever**: `1 Cobble + 1 Planks → 1 Lever`
- **Stone Button**: `1 Cobble → 2 Stone Button`
- **Pressure Plate**: `2 Planks → 1 Pressure Plate`
- **Redstone Torch**: `1 Redstone Dust + 1 Wood → 2 Redstone Torch` (mirrors the torch recipe shape)
- **Redstone Lamp**: `4 Redstone Dust + 2 Glass → 1 Redstone Lamp`

All results are `kind: "block"` ⇒ they land in the **Building** recipe-book category automatically (`KIND_TO_CATEGORY`, recipes.ts:677). Recommend *not* adding a "Redstone" category in lite (that touches `RecipeCategory` + order + `recipeCategory()`); flag as an open question. Item-source hints ("craft it") derive automatically from the recipes (`itemSources.ts`).

**tickRedstone pseudocode** (collect-then-apply, single `worldMeshDirty` — explosion.ts discipline; **never touches `drainEdits`**, which is the server's):

```
timer += dt; if timer &lt; REDSTONE_TICK_SECONDS return; timer = 0   // ≤1 pass per step
changed = false

// Phase 1 — inputs &amp; self-heal (iterate cells; deletions safe on a Set)
occupied = feet cells of all players + all mobs (D6 formulas)
for idx of rs.cells:
  b = world.blocks[idx]
  if !isRedstoneBlock(b): cells.delete(idx); buttonTimers.delete(idx); continue
  if isRedstoneOverlay(b) &amp;&amp; support below is not solid non-overlay:
      blockChanges.set(x,y,z, Air); cells.delete(idx); changed = true; continue   // orphan pop
  if isPlate(b) &amp;&amp; (occupied.has(idx)) !== isRedstoneOn(b):
      blockChanges.set → flipped id; emit plateToggled{on}; changed = true
  if b === RedstoneButtonOn:
      t = buttonTimers.get(idx)                       // undefined after reload → heal
      if t === undefined || t - REDSTONE_TICK_SECONDS &lt;= 0:
          blockChanges.set → RedstoneButton; buttonTimers.delete; changed = true
      else buttonTimers.set(idx, t - REDSTONE_TICK_SECONDS)

// Phase 2 — power graph from the CURRENT grid (post phase-1)
powered = Set(); wireBudget = Map&lt;idx, number&gt;; queue = []
for idx of cells where block ∈ {LeverOn, RedstoneButtonOn, PressurePlateOn, RedstoneTorch(on)}:
  for n of 6 neighbors, SKIPPING the below-neighbor when the source is a torch:   // D4
    powered.add(n)
    if isWire(block(n)): relaxBudget(n, REDSTONE_WIRE_RANGE)
while queue: (w, budget) = pop
  powered.add(w); powered.add(each of w's 6 neighbors)          // wire powers what it touches
  if budget &gt; 1: for c of 8 wire-step candidates (4 horiz × Y ∈ {0,+1,−1}):
    if isWire(block(c)): relaxBudget(c, budget − 1)             // keep best budget per cell
// relaxBudget: enqueue only if new budget &gt; recorded budget (bounded, no revisits)

// Phase 3 — outputs (write only on change)
for idx of cells:
  b = block(idx)
  if isWire(b)          &amp;&amp; (wireBudget.has(idx)) !== isRedstoneOn(b): flip; changed = true
  if isRedstoneLamp(b)  &amp;&amp; powered.has(idx)      !== isRedstoneOn(b): flip; emit lampToggled{on}; changed = true
  if isRedstoneTorch*(b): want = !powered.has(idx below); if want !== isRedstoneOn(b): flip; changed = true
// Consumers OUTSIDE the tracked set — discovered by scanning the powered set:
doorPowered = Set()
for idx of powered:
  b = block(idx)
  if isDoorBlock(b): doorPowered.add(lower-half index via doorState)
  else if b === Tnt: primeTnt(state, x, y, z, emit)             // no-op if already lit
for lower of doorPowered − prevDoorPowered: force both halves open (doorBlock pair logic); emit doorToggled{open:true}; changed = true
for lower of prevDoorPowered − doorPowered: if still a door: force closed; emit doorToggled{open:false}; changed = true
prevDoorPowered = doorPowered

if changed: state.worldMeshDirty = true
```

Doors and TNT need **no tracking** — they're found through the powered set, so explosions/mining of consumers need zero bookkeeping.

## 5. Save / reload / self-heal summary

- Power state = id parity; lever/plate/wire/lamp/torch states persist in the diff and are **re-derived to consistency within one redstone tick of load** (first pass recomputes everything from the grid).
- Pressed button + empty `buttonTimers` after reload → popped back on first pass (§D2).
- `prevDoorPowered` empty after reload → a still-powered door registers as a rising edge and re-forces open (idempotent if already open — write-on-change suppresses the churn; emit doorToggled only when a cell actually flips).
- Explosion/mining destroying circuit cells → self-heal deletion; orphaned overlays popped.

## 10. Risks &amp; open questions

**Risks**
- **Clock churn**: an oscillating circuit sets `worldMeshDirty` + relights + broadcasts a handful of block deltas every 0.1–0.2 s. Same cost class as mining spam and bounded by circuit size; stable circuits cost zero (write-on-change). Flagged in tuning.md; `REDSTONE_TICK_SECONDS` is the throttle.
- **Save-diff growth**: each wire cell adds one diff entry (it would anyway, being player-placed); on/off flips mutate entries in place — no growth. A world saved mid-clock reloads consistent after one pass.
- **`pushBlockCuboid` signature change** touches the door path — covered by existing door meshing behavior; keep the refactor mechanical.
- **Floor-mount-only components** (no wall buttons/levers, no facing ids) — a deliberate lite simplification; add facing variants later as new id blocks if wanted.
- AO/`hasSupportUnderPlayer` treat overlay cells as solid in two cosmetic spots — negligible, matches the door trade-off; noted, not changed.
