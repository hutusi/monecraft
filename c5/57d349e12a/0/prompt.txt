## CLIENT ONLINE PATH — findings (file:line)

The single most important fact for "Nether in multiplayer": **the wire protocol has no dimension concept anywhere**, and dimension travel is explicitly gated to single-player. Everything below flows from that.

### 1. Replica engine

The client runs a **full local `GameEngine` in "replica" mode**, not a thin replica — same class the server and SP use, constructed with `authority: "local", replica: true, bootPlayer: false` from the WELCOME seed. `lib/net/NetworkSession.ts:279-296`.

- What the replica simulates vs. receives: `lib/game/engine/GameEngine.ts:207-214` (doc) and the actual gate `GameEngine.ts:636-646`. In replica mode `step()` advances **only** the local player's predicted movement + cosmetic mining progress + day-clock smoothing. Mobs, spawns, TNT, projectiles, vitals are **replicated**, never simulated.
- Server block-changes land via `applyBlocks` → `state.blockChanges.set(...)` which relights locally, `NetworkSession.ts:521-537`, driven by the `tick` frame's `message.blocks`, `NetworkSession.ts:564`.
- Mob poses: `upsertReplicaMob` + per-mob `PoseBuffer`, `NetworkSession.ts:427-465`; sampled into `state.mobs` in `afterFrame`, `NetworkSession.ts:847-854`.
- Local-player private state (vitals, inventory, position when mounted) overwritten from `SelfDelta` in `applySelfDelta`, `NetworkSession.ts:467-497`.
- **Client-side prediction**:
  - Movement: replica `tickPlayerMotion` for the primary only, `GameEngine.ts:640-641`; pose streamed at tick rate in `afterFrame`, `NetworkSession.ts:809-826`.
  - Placement: optimistic via `engine.predictPlaceBlock()` recorded in a **prediction ledger**, `NetworkSession.ts:311-314`; ledger in `lib/net/prediction.ts`.
  - Mining: predictive break commits locally (`authority: "predict"`), `GameEngine.ts:642-646`; captured from the journal each frame and ledgered, `NetworkSession.ts:781-793`.
  - Reconciliation/echo-suppression against the server journal: `NetworkSession.ts:521-537, 583-600`; expiry/revert `NetworkSession.ts:799-806`.
- The command split (presentation stays local, gameplay goes up) is `engine.routeDispatch`, `NetworkSession.ts:300-319`, with `LOCAL_COMMANDS` at `NetworkSession.ts:76`.

### 2. Remote players

- Rendered by `lib/game/render/remotePlayerVisuals.ts` — one procedural humanoid + canvas name-tag sprite per entry in `state.players` minus the primary, `remotePlayerVisuals.ts:69-119`; name tag `makeNameTag` `:26-45`.
- Driven from `GameRenderer.sync` → `remotePlayerVisuals.sync(state.players, state.primaryPlayerId, this.remotePlayerInfo, ...)`, `lib/game/render/GameRenderer.ts:227`; names/skins injected from the session, `useMinecraftGame.ts:372` and `GameRenderer.ts:102-103`.
- Poses live in `state.players` (a `Map&lt;PlayerId, PlayerState&gt;`), written by interpolation sampling in `NetworkSession.afterFrame`, `NetworkSession.ts:838-846`, fed by per-player `PoseBuffer`s, `NetworkSession.ts:567-575`.
- **Single-world-volume assumption (critical for your plan)**: every remote player is a `PlayerState` in the same `state.world`/`state.dimension` replica. There is no per-player dimension on the client — `RosterEntry` (`protocol.ts:84`) and `PlayerPose` (`protocol.ts:137`) carry only x/y/z/yaw/pitch. A far-away or "out of area" player is only distance-culled by rendering; there is no notion of a player being in a different dimension. `remotePlayerVisuals.sync` renders **all** of `state.players` unconditionally, so a player in another dimension would still draw at its raw coordinates.
- Server-side pose validation also assumes one volume: `applyRemotePose`, `GameEngine.ts:555-579`.

### 3. Dimension-sensitive presentation

Dimension is a **construction-time** property of the engine (`state.dimension`, `state.ts:309-313`) and the renderer. Nothing switches live — swap-on-travel **remounts** engine+renderer together.

- **Sky/fog/light/celestials/precipitation**: `lib/game/render/dimensionProfiles.ts` (whole file; `DIMENSION_PROFILES` `:28-50`). Renderer is built for `DIMENSION_PROFILES[gameEngine.state.dimension]`, `useMinecraftGame.ts:360` and `GameRenderer.create` `GameRenderer.ts:115`. `skyLightFloor` is **baked into the shader source**, so it genuinely cannot change without a renderer rebuild (`dimensionProfiles.ts:8, 15-25`).
- **Minimap**: keys off `state.dimension === "nether"` per frame for the roofed-column scan, `lib/game/render/minimap.ts:55`; color logic `lib/game/render/minimapColors.ts:11`. (Minimap reads `state.dimension` live each `sync`, unlike the renderer.)
- **Compass/tracking HUD**: `components/game/TreasureCompass.tsx` and boss tracking (`lib/game/bossTracking.ts`) key off treasure/boss snapshot data, **not** dimension directly.
- **Music/ambience**: keys off **daylight + biome, not dimension** — `moodFor(state.daylight, stableBiome)`, `lib/game/audio/audioDirector.ts:449`; `moodFor(daylight, biome)` `lib/game/audio/musicBrain.ts:36`. So music/ambience will NOT react to a dimension change on its own; today the Nether just gets pinned-daylight mood. This is a gap for your plan.
- **What must react to a NET-driven dimension change**: the renderer (rebuild with the new profile), the minimap (already reads live), and — if you want it — the music brain. Today the only trigger for any of this is a full engine+renderer **remount** via `onReloadWorld` (see #4), which online play deliberately never does.

### Bottom line for "Nether in multiplayer"
There is no dimension on the wire (`protocol.ts` WELCOME/WorldSync/Tick/RosterEntry/PlayerPose all lack it), the client replica is hard-wired to one `state.dimension` at construction, remote players are assumed to share one world volume (`remotePlayerVisuals.ts:69-119`), presentation swaps happen only via full engine+renderer **remount** on the SP-only `dimensionTravel` path (`useMinecraftGame.ts:355-360, 481-493`), and online portal use is currently refused outright (`portal.ts:124-126`). A net-driven dimension change has no existing path — it needs new protocol fields, a client story for a second world volume, and a way to rebuild the renderer without the SP save-and-remount dance.</result>
