## 5. OVERALL ENGINE/ARCHITECTURE

### Three-Layer Architecture
**React UI** (`lib/game/useMinecraftGame.ts`, `components/`) → **GameEngine** (headless, no DOM) → **Voxel World** + **GameRenderer** (Three.js) + **AudioDirector**

### Engine Organization (`lib/game/engine/`)
**Core:**
- `GameEngine.ts` — state machine, command dispatch, step(dt, input), snapshots
- `state.ts` — GameState (player, inventory, mobs, day clock, mining progress, effects, stats, advancements)
- `commands.ts` — Command union (all UI intents enter here)
- `blockChanges.ts` — delta tracker for saves

**Systems (`systems/` directory):**
1. **playerMotion.ts** — movement physics, knockback, flight
2. **playerStats.ts** — hunger, health regen, water/lava/drowning damage, armor bypass hazards
3. **mining.ts** — block breaking, placement, reach
4. **dayNight.ts** — daylight curve formula
5. **weather.ts** — transient rain/snow simulation
6. **randomTicks.ts** — crop growth, sapling growth, grass spread
7. **spawnDirector.ts** — night hostile spawning, dungeon spawners, caps
8. **mobAI.ts** — wander, aggro, flee, ranged kiting, daylight burn
9. **projectileAI.ts** — arrow gravity integration, swept collision tests
10. **spears.ts** — thrown spear state, gravity, terrain/mob collision
11. **breeding.ts** — feed-to-love timers, pairing, baby maturity
12. **combat.ts** — attack command, bow fire, spear throw
13. **interact.ts** — right-click precedence (throw spear → feed animal → interact block → summon boss → use item → place block)
14. **mining.ts** (also) — block breaking/placement
15. **fishing.ts** — bobber cast/bite/reel mechanics
16. **explosion.ts** — TNT/creeper/boss splash damage
17. **statusEffects.ts** — effect ticks (regen/poison), accumulators
18. **xp.ts** — XP award, level tracking
19. **advancements.ts** — stat bumping, advancement unlock evaluation
20. **dungeon.ts** — dungeon loot chest generation on first open/break

### Renderer (`lib/game/render/`)
- `GameRenderer.ts` — scene/camera, sync(state) → Three.js update, dispose()
- **Camera modes:** 1st-person, 3rd-person rear/front boom (clamped against walls)
- **World mesh:** Single mesh per visible region, rebuilt on player RENDER_GRID (20-block) crossing or worldMeshDirty
- **Lighting:** Per-voxel sky+block light baked at load, patched per edit, no serializaton (derived cache)
- **Mob models:** Procedural box humanoids with leg gait + bob animation
- **Projectiles:** Arrow sprites oriented along velocity, single shared geometry
- **Particles:** Procedural bursts (block shards, mob death, eat crumbs, dust)
- **Atmosphere:** Procedural sky, stars, moon, clouds, weather precipitation
- **Minimap:** 128×128 canvas, 10Hz refresh, rebuilt on 16-block grid or worldMeshDirty
- **Skins:** 6 player palettes, persisted on profile, no image assets

### Audio (`lib/game/audio/`)
- Procedural sound (ZZFX parameter arrays), no audio files
- `audioDirector.ts` — event handler for block break/place, hurt, mob attacks, etc.
- **Music:** Generative ambient pads, day/night mood, biome flavor (5s hysteresis), ducks while paused

## PHASE 0b — Allegiance + mob-vs-mob combat (PR1, no save bump)

### The allegiance model (`lib/game/engine/state.ts`)
Keep `hostile: boolean` (it is load-bearing for caps, `despawnHostiles`, `HOSTILE_CAP` directors, the snapshot `passiveCount`/`hostileCount`, and the health-bar gate). **Add a coexisting `faction`:**

```
Faction = "wild" | "hostile" | "ally" | "villager" | "raider"
```

Add to `MobState`:
- `faction: Faction` — set at spawn (`pushMob`) from a `FACTION_BY_KIND` map; overridden on tame (Phase 1) and for raiders (Phase 4).
- `owner?: "player"` — pet ownership (Phase 1; unused here but define the field now so the persistence shape is stable).
- `targetId: number | null` — session-only cache of the mob it is currently fighting.
- `retargetTimer: number` — session-only throttle for the enemy scan.

`hostile` stays the *threat/cap* axis; `faction` is the *targeting* axis. Initial mapping: sheep/chicken/horse/cow/pig → `wild`; zombie/skeleton/spider/creeper/boss → `hostile`; villager → `villager`. (`ally`/`raider` arrive in later phases.) `pushMob` (`spawnDirector.ts:32`) sets `faction` from the map; `spawnBaby` (`breeding.ts:52`) inherits the parent's `faction`/`owner`.

### Shared target selection (`lib/game/engine/systems/mobAI.ts`)
One helper, `selectMobTarget(state, mob)`, driven by a small enmity table:

```
ENEMIES: ally → {hostile, raider}; hostile → {villager, ally}; raider → {villager, ally}; wild,villager → ∅
```

Behaviour: only "fighter" factions (`ally`/`hostile`/`raider`) scan. A fighter rescans only when `retargetTimer ≤ 0` **or** its cached `targetId` is dead/out of range — then one linear pass over `state.mobs` finds the nearest enemy-faction, alive mob within `detectRange`, reusing the existing scratch vectors (no allocation). Reset `retargetTimer` to `MOB_RETARGET_SECONDS` (~0.6 s). This keeps the all-mobs loop **O(N)** per frame for steering and amortizes the O(N) scan to ~1–2 Hz per fighter, so worst-case stays well under budget for the ~70-mob population.

Player aggro is preserved as today for backward compatibility with every existing test: a `hostile` still prefers the player when the player is within `detectRange` (the existing `activeHostile` block). Only when no player aggro applies does it fall through to a mob target. A `raider` (Phase 4) inverts the priority (villagers first, player second). `villager`/`wild` never fight: villagers gain a *flee-from-nearest-hostile/raider* branch (mirror the existing animal-flee branch at `mobAI.ts:166`, but flee the nearest enemy mob instead of the player).

### Striking a mob target (not the player)
When a fighter is in melee reach + LOS of its `targetId` and `attackTimer ≤ 0`: lower `target.hp` by `attackDamage` (apply knockback to the target via the same `addScaledVector` pattern as `tryAttackMob`, `combat.ts:89`), emit `mobAttacked`, reset `attackTimer`. **Difficulty `dmgScale` is NOT applied to mob-vs-mob** — `mobDamageMultiplier` scales damage *to the player* only; mob-vs-mob uses raw `attackDamage`. Deaths are still handled by the existing post-loop sweep, never mid-loop (preserves the splice-safety invariant).

**Melee-only by design.** Ranged mob-vs-mob is explicitly out of scope: the projectile hit-filter is a binary `fromPlayer` flag (`projectileAI`/`state.ts:71`), so a mob arrow can only hit the player. Making arrows team-aware is a separate, larger change. Pets (Phase 1) and raiders (Phase 4) are therefore **melee fighters**. Call this out in the PR.

### Kill / loot / XP flow when a mob is the killer (`GameEngine.ts:822`)
Generalize `removeMobAt(index, opts?: { credit?: boolean; lootingLevel?: number })`, default `credit: true` so **every existing call site is unchanged** (player melee, arrows, spears, explosions, daylight burn all keep crediting). The death sweep in `mobAI.ts` computes credit from the **victim's faction**:

```
credit = victim.faction ∈ {wild, hostile, raider}   // false for {ally, villager}
```

Rationale: a pet (`ally`) killing a `hostile`/`raider` should still drop loot into your inventory and award XP ("your wolf hunts for you"), so a *victim-faction* rule (not attacker) is correct. A slain villager or pet yields the player nothing — and crucially closes the XP-leak where the player would otherwise farm XP off raiders/hostiles killing each other. (Today villager/ally drop tables are empty and XP is 0, so this is mostly a correctness guard, but it must be explicit before professions/raids give those factions value.) The boss-victory branch keys on `kind === "boss"` and is untouched.

### Save/worldgen impact
None. `MobState` is not serialized yet, so the new fields are session-only.

## PHASE 0a + 1 — Companions + mob persistence (PR2, save v13→v14)

### 0a. Mob persistence

**What to serialize.** A minimal `SavedMob` carrying only irreplaceable identity/state; everything else is re-derived from the template:

```
SavedMob = { kind, x, y, z, hp, faction, owner?, sitting?, ageTimer? }
```

- **Persist:** `kind` (validated against a known-kinds set on load — drops unknown kinds for version drift), position (`x,y,z` floats), `hp` (finite, clamp to `(0, template.hp]`; ≤0 drops the mob), `faction`, `owner`, `sitting` (pet stay-state), and optional `ageTimer` (so a bred puppy stays a baby).
- **Re-derive from `MOB_TEMPLATES` on restore:** `speed`, `detectRange`, `attackDamage`, `attackCooldown`, `halfHeight`, plus fresh `direction`/`yaw`/`bobSeed`/`turnTimer`/`attackTimer`/`moveSpeed`.
- **Never persist (transient):** `fedTimer` (love window), `summonTimer`, `fuseTimer`, `targetId`, `retargetTimer`, `id` (fresh ids assigned on restore — see below).

**Minimal-persistence policy (recommended): persist only the `persistent` set — tamed pets ∪ village residents — NOT the whole population.** Justification:
1. Ambient wildlife and hostiles are *fungible* — `spawnInitialMobs` (`spawnDirector.ts:81`) re-seeds them every boot anyway, so persisting them is wasted bytes and would double the population on load.
2. It bounds the save: a save can't balloon with hundreds of wandering animals.
3. It avoids serializing volatile combat/AI state on throwaway mobs.
4. The boss and creepers are already deliberately transient (`fuseTimer`/`summonTimer`/`victory` never saved) — persisting a mid-fight boss reopens minion-cap and victory-flag hazards. Keep them transient, consistent with the existing design.

The persistence predicate is `isPersistentMob(mob) = mob.owner != null || mob.faction === "villager"`. In Phase 1 only pets match; Phase 2 marks village residents (also `villager`, so they match automatically).

**`serializeMobs` / `restoreMobs`** in `lib/game/save.ts` (mirroring `serializeContainers`/`readContainers`):
- `serializeMobs(mobs)` filters `isPersistentMob` and maps to `SavedMob`.
- `restoreMobs(save, surfaceYAt)` validates each entry, rebuilds a full `MobState` via a template-based factory (the same construction as `pushMob`), **re-grounds y** via `surfaceYAt(x,z) + halfHeight` (so a pet saved on now-air or buried terrain lands on the regenerated surface; `tickMobs` re-grounds every tick anyway), clamps x/z into world bounds (drop if hopeless), and assigns **fresh sequential ids** with `nextMobId` advanced past them. Fresh ids are safe because the renderer is a cold boot too (`mobVisuals` reconciles by id from empty).

**`migrateSaveV13toV14`** is a pure version bump (`mobs` absent ⇒ empty). `readSave` gains `if (migrated.version === 13) migrated = migrateSaveV13toV14(migrated)` and accepts `version === 14`. Types: rename current `SaveData`→`SaveDataV13`, add `SaveData = Omit&lt;SaveDataV13,"version"&gt; &amp; { version: 14; mobs?: SavedMob[] }`.

**Engine wiring (`GameEngine.ts` constructor):** restore persisted mobs **before** `spawnInitialMobs` (line 286). `spawnInitialMobs` still runs unconditionally (it seeds fungible wildlife/hostiles at fixed counts, no cap check) so the world stays alive; restored pets/residents simply pre-exist. Cap interaction: `PASSIVE_CAP`/`HOSTILE_CAP` only gate *breeding* and *night/dungeon spawns* (both count live mobs), so a few extra restored mobs self-limit those — there is no crash and no runaway. `serialize()` adds `mobs: serializeMobs(state.mobs)`.

**Re-attach to renderer:** nothing special. On the next `renderer.sync`, `mobVisuals.sync` sees ids it hasn't created and builds models. Pets are non-hostile ⇒ no health bar (the existing gate). The pet's `owner`/`sitting`/`faction` drive an optional sit pose + collar tint (below).

**Edge cases (explicit):** unknown `kind` → dropped; non-finite/≤0 `hp` or non-finite coords → dropped; out-of-bounds position → clamped or dropped; mob on now-air terrain → re-grounded; version drift → migration + per-entry validation tolerate it.
