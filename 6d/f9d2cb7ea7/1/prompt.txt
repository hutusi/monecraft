# Seam A — Boardable vehicles in multiplayer

## How boarding/steering works today (`lib/game/engine/systems/vehicles.ts`)

- **Raft right-click boarding**: `tryBoardAimedVehicle` (`vehicles.ts:205`) → `aimedVehicle` raycast (`vehicles.ts:184`) → `mountVehicle` (`vehicles.ts:135`). `mountVehicle` sets `vehicle.rider = player.id`, `player.mountedVehicleId = vehicle.id`, then `syncPlayerToVehicle`.
- **Ship step-on boarding**: the non-mounted branch of `tickVehicles` (`vehicles.ts:259-272`) — for each unridden ship it projects the player into the hull's local frame and calls `mountVehicle` if they're standing on the deck. **This path is NOT authority-gated.**
- **Mounted steering**: mounted branch of `tickVehicles` (`vehicles.ts:240-256`). Reads `input.move.forward/back` (thrust) and `input.move.left/right` (yaw), integrates `mounted.position`, reverts on `!canOccupy` (`vehicles.ts:121` — water-support + bounds + overlap), then `syncPlayerToVehicle` (`vehicles.ts:176`) pins `player.position` to `vehicle.position.y + 0.16`, zeroes velocity, `onGround = true`.
- **Water support**: `vehicleHasWaterSupport` (`vehicles.ts:97`) — every rotated footprint corner must have Water below + Air at deck level.
- **Dismount**: `input.move.crouch` triggers `dismountVehicle` (`vehicles.ts:145`) — searches offset cells for a non-colliding spot, clears `rider`/`mountedVehicleId`.

## Where boarding is gated OFF

- **The one explicit gate**: `GameEngine.ts:857-859`, inside the `placeBlock` command handler:
  ```
  if (this.authority !== "server" &amp;&amp; !this.replica &amp;&amp; tryBoardAimedVehicle(state, player)) break;
  ```
  So raft right-click boarding is skipped on both server and replica. **Un-gating Seam A starts here.**
- **`applyRemotePose` early-out**: `GameEngine.ts:448-449` — `if (player.mountedVehicleId !== null) return { accepted: false }`. This is the mechanism you KEEP (server owns the mounted pose; the client's streamed pose is rejected). Note `room.ts:282` still calls `setPlayerInput(...move...)` on every pose even when rejected, so **steering intents already reach the server** through `player.input` → `tickVehicles`.
- **`stepPlayer` movement selection**: `GameEngine.ts:615-627`. Three branches: `mounted` → `tickVehicles` drives the body (zeroed move-summary); `authority === "server"` unmounted → consumes `player.remoteMove` synthesized from accepted poses; `local` → `tickPlayerMotion`. Critically, `tickVehicles` is called in ALL three branches — so **ship step-on already fires on the server today**, but there's no channel to tell the owning client they got mounted, which is the latent desync.

## The two real gaps (outbound replication)

The server can already drive a mounted player from intents. What's missing is getting the authoritative result back:

1. **The owning client doesn't learn it's mounted and doesn't get its own authoritative position.** `collectPlayerPoses` (`room.ts:463-470`) excludes `self`, and the replica's `step()` (`GameEngine.ts:519-530`) unconditionally runs `tickPlayerMotion(primary...)` for the local player — it never checks `mountedVehicleId` (which is never set on the replica's `self`). So the owner keeps free-walking-predicting while the server thinks they're riding → rubber-band. This is almost certainly why boarding was cut.
2. **Vehicles are never replicated live, and never even restored on join.** `WorldSync.vehicles` is populated server-side (`room.ts:458` via `serializeVehicles`), but **`applyWorldSync` in `NetworkSession.ts:231-246` ignores `sync.vehicles` entirely** — the replica's `state.vehicles` stays empty, so `vehicleVisuals.sync(state.vehicles)` (`GameRenderer.ts:215`) renders nothing. There is also no live vehicle-pose channel in `TickMessage`.

## Cleanest wiring for Seam A (reuse points)

- **Un-gate** `GameEngine.ts:859` so `tryBoardAimedVehicle` runs under server authority (it arrives as a `placeBlock` cmd; `placeBlock` is already a network command — not in `LOCAL_COMMANDS` at `NetworkSession.ts:71` — so a right-click already round-trips to the server via `sendCmd`).

- **Per-player state is already the source of truth.** `PlayerState` (`lib/game/engine/state.ts:31`) owns `stats: Map&lt;string,number&gt;` (`:57`), `advancements: Set&lt;string&gt;` (`:59`), `xp` (`:55`), `inventory`, `hearts`, etc. `GameState.players: Map&lt;PlayerId,PlayerState&gt;` (`state.ts:270`) holds one per player.
- **The primary alias trap.** `state.stats`, `state.advancements`, `state.player`, etc. are accessor aliases onto the *primary* player, installed by `installPlayerAliases` (`lib/game/engine/players.ts:155-187`, key list `:21-46`). The file's own doc warns: "ENGINE SYSTEMS MUST NOT USE THEM" (`players.ts:14-17`). A headless server room has a `primaryPlayerId` that points at nobody real.
- **Player helpers** (reuse points): `getPlayer(state,id)` (`players.ts:68`), `mustGetPlayer` (`:72`), `primaryPlayer` (`:78`), `nearestPlayerTo(state,x,z)` (`:87`), `nearestTargetablePlayer` (`:123`).
- **Per-player serialization already exists (SavedPlayer v17).** `serializePlayer` writes `stats: serializeStats(player.stats)` and `advancements: [...player.advancements]` (`GameEngine.ts:1073-1074`); `restorePlayerFields` restores them per-player (`:1096-1099`). Codecs: `serializeStats`/`restoreStats`/`restoreAdvancements` in `lib/game/save.ts:506-535`. **So persistence needs no change for C** — only the live accrual + wire path do.

## Seam C — Per-player advancements &amp; stats on the server

### Current data flow
1. **Single emit chokepoint.** `GameEngine.emit` (`GameEngine.ts:1150-1155`) pushes the event, then calls `this.observeProgress(event)` for everything except `advancementUnlocked` (recursion guard).
2. **observeProgress records to primary only** (`GameEngine.ts:1166-1174`):
   ```
   const primary = this.state.players.get(this.state.primaryPlayerId);
   if (!primary) return;                       // ← server rooms: no primary → tracks NOTHING
   recordEvent(primary, event);
   for (const id of evaluateAdvancements(primary)) {
     primary.advancements.add(id);
     this.emit({ type: "advancementUnlocked", id, name: ADVANCEMENTS_BY_ID[id].title });
   }
   ```
   The doc comment at `:1157-1164` explicitly names this as the known MP gap.
3. **advancements.ts is pure and per-player already.** `recordEvent(player, event)` (`advancements.ts:71-127`) folds one event into `player.stats`; `recordTick(player, dt, dist)` (`:134-137`) bumps `play_time`/`distance_walked`; `evaluateAdvancements(player)` (`:245-252`) returns newly-earnable ids from `player.stats` vs the `{stat, threshold}` registry (`ADVANCEMENTS`, `:168-234`). None of these touch the primary — they take a `PlayerState`. **Fully reusable as-is.**
4. **`recordTick` is already correctly attributed.** `stepPlayer` calls `recordTick(player, dt, move.horizontalDistance)` with the real acting player (`GameEngine.ts:631`). So the per-frame counters already accrue per-player; only the *event*-driven path (`observeProgress`) is mis-attributed.

### The attribution gap
- **`GameEvent` does NOT carry a playerId** (union at `state.ts:513-575`). Only `playerJoined`/`playerLeft` have `playerId`. World events (`blockBroken`, `mobDied`, `crafted`, `bowFired`, `mobBred`, …) are anonymous.
- **`emit` takes only `(event)`** — there is no `emit(event, playerId?)` today (`GameEngine.ts:1150`). Every call site (`this.emit({...})`) passes a bare event. So the acting player is known at each emit site (dispatch has `player` at `:672`; `stepPlayer` has `player`) but is *dropped* at the emit boundary.

### Wire path — stats/advancements do NOT ride the self-delta today
- `SelfDelta` type (`lib/net/protocol.ts:122-135`) carries inventory/armor/selectedSlot/hearts/hunger/oxygen/xp/effects/isDead/respawnSeconds/gameMode/sleeping. **No `stats`, no `advancements`.**
- `Room.buildSelfDelta` (`server/room.ts:502-536`) diffs exactly those fields against `conn.shadow`; the `shadow` type (`room.ts:63-76`) has no stats/advancements slots.
- `NetworkSession.applySelfDelta` (`lib/net/NetworkSession.ts:288-305`) applies exactly those fields to `self`.
- **Advancement unlocks currently reach clients only as loose events**: `advancementUnlocked` is an emitted `GameEvent`, drained by the server tick (`room.ts:372` `consumeEvents()`), and broadcast to *everyone* in `TickMessage.ev` (`room.ts:395` `ev: events`). On the client they flow through `pendingEvents`/`onEvent` (`NetworkSession.ts:358-361`) into the shell's toast drain — but they are **not per-recipient** and don't update any client's `stats`/`advancements` maps.

### What Seam C needs
- **(a) Attribute each event to the actor.** Add an optional actor to the emit boundary — e.g. `emit(event, actorId?: PlayerId)` (`GameEngine.ts:1150`) — and thread the acting `PlayerId` from the sites that already hold a player: the whole `dispatch` switch (actor = `player`, resolved at `:672`), `removeMobAt` (actor = the crediting receiver — ties into Seam D), and system callbacks that emit (combat/mobAI/projectileAI pass `emit` down). Systems that emit world events without an obvious actor (mob death sweep, explosions) inherit the same actor plumbing you build for Seam D.
- **(b) Fold into that player's maps.** Change `observeProgress` (`:1166`) to `observeProgress(event, actorId?)`: resolve `actor = actorId ? getPlayer(state, actorId) : primary`, then `recordEvent(actor, event)` + `evaluateAdvancements(actor)` exactly as now. The `advancementUnlocked` re-emit should carry the same actorId so the toast is routed to the right client. Reuse `recordEvent`/`evaluateAdvancements`/`ADVANCEMENTS_BY_ID` unchanged.
- **(c) Send per-player unlocks + stat counts down the self-delta.** Extend `SelfDelta` (`protocol.ts:122`) with `advancements?: string[]` and `stats?: Array&lt;{id;value}&gt;` (or a changed-since-last subset); diff them in `buildSelfDelta` (`room.ts:508`) against new `shadow` fields (`room.ts:63`); apply them in `applySelfDelta` (`NetworkSession.ts:288`) onto `self.advancements`/`self.stats`. This makes each client's own `advancementsUnlocked` snapshot count (`state.ts:483`, built at `GameEngine.ts:1606` from `state.advancements.size`) correct for a server room. Reuse `serializeStats`/`restoreStats` (`save.ts:506/515`) as the codec.
- Note the recursion guard (`emit` skips `observeProgress` for `advancementUnlocked`, `:1154`) must be preserved when you add the actor param.

## Seam D — Mob-kill credit for indirect kills

### The single credit sink
`removeMobAt` (`GameEngine.ts:1296-1322`) is the one place loot + XP land:
```
private removeMobAt = (index, lootingLevel = 0, credit = true, creditTo?: PlayerState) =&gt; {
  ...
  const receiver = creditTo ?? state.players.get(state.primaryPlayerId) ?? null;   // ← default = primary
  const drops = credit &amp;&amp; receiver &amp;&amp; mob.ageTimer &lt;= 0 ? rollMobDrops(...) : [];
  if (receiver) { ...adjustSlotCount into receiver.inventory...
    if (credit &amp;&amp; mob.ageTimer &lt;= 0) awardXp(receiver, xpForMob(mob.kind), this.emit); }
  ...
}
```
- **`creditTo` is a prepared-but-unused seam: it has ZERO callers today** (grep confirms only the definition `:1296` and the `creditTo ?? primary` fallback `:1302`). Every path falls through to the primary.
- `awardXp(receiver, ...)` (`systems/xp.ts`, imported `GameEngine.ts:122`) already targets an explicit `PlayerState`, and loot goes to `receiver.inventory`. **The receiver plumbing is per-player-ready — only the choice of receiver is wrong.**

### The four kill paths and their attribution assumptions
1. **Direct melee** — `dispatch` `attack` case (`GameEngine.ts:869-893`) calls `tryAttackMob(state, player, …, this.removeMobAt, …)` (`:879-887`). `tryAttackMob` (`combat.ts:75-100`) invokes `onMobKilled(bestIndex, lootingLevel)` (`:98`) — **only index + looting, no `creditTo`**. So even a *direct* kill credits the primary, not `player`. The attacker (`player`, `GameEngine.ts:672`) is in scope but never forwarded. Minimal fix: pass a closure `(i, looting) =&gt; this.removeMobAt(i, looting, true, player)`.
2. **Player arrows** — `projectileAI.ts:124` `deps.removeMobAt(hitMobIndex)` (no credit/creditTo). The projectile only knows `fromPlayer: boolean` (`state.ts:155`, set in `spawnArrow` `projectiles.ts:37`) — **no shooter id**. `ProjectileTickDeps.removeMobAt` is typed `(index)=&gt;void` (`projectileAI.ts:9`), so it *can't* pass credit even if it wanted to. Fix requires adding an `owner?: PlayerId` to `ProjectileState`, capturing it at `tryFireBow` (`combat.ts:113-136`, currently sets `fromPlayer: true`), widening the deps signature, and forwarding to `removeMobAt`.
3. **Thrown spears** — `spears.ts:93` `removeMobAt(hitIndex)`; the param is typed `(index)=&gt;void` (`spears.ts:53`). `ThrownSpearState` (`state.ts:166-175`) has `itemId` but **no owner**. Same shape of fix as arrows.
4. **Explosions &amp; mob-vs-mob / pet kills (the post-loop sweep)** — `mobAI.ts:504-512`:
   ```
   if (dead.hp &lt;= 0) deps.removeMobAt(i, 0, CREDITED_FACTIONS.has(dead.faction));
   ```
   Passes a `credit` boolean (from `CREDITED_FACTIONS`, `mobAI.ts:82`) but **no `creditTo`** → primary. This is the exact "pet kill / creeper / explosion defaults to primary" path. `MobTickDeps.removeMobAt` typed `(index, lootingLevel?, credit?)` (`mobAI.ts:226`) — no creditTo slot. `explode` (`explosion.ts:58`) never removes mobs (only lowers hp, `:56`), so all explosion kills resolve through this sweep; `ExplosionDeps` (`explosion.ts:10-15`) carries no owner. TNT is lit by a player (chain at `explosion.ts:79-88`, entry `:176`); creeper blasts (`mobAI.ts:488`) have no player actor.

### What Seam D needs
- Thread a **killer `PlayerId`** to `removeMobAt`'s `creditTo`, wired at each kill site: melee → `player`; arrows/spears → a new `owner` field on `ProjectileState`/`ThrownSpearState` captured at spawn; explosion-driven sweep → an actor carried on the mob death (e.g. "last damaged by" or, for pets, `dead.owner`; for a pet's *own* kill of an enemy, credit `mob.owner`). Widen the three `removeMobAt` dep signatures (`projectileAI.ts:9`, `spears.ts:53`, `mobAI.ts:226`) to carry the creditTo/id. The receiver→inventory/XP machinery underneath is untouched.
- This dovetails with Seam C: the same actor you resolve for credit is the actor whose `mobDied`/`pickedUp`/XP events should attribute progression.
