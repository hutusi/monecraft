## Summary

The engine's single block-mutation chokepoint is **`BlockChangeTracker.set()`** at `/Users/hutusi/workspace/ai/david/monecraft/lib/game/engine/blockChanges.ts:37-52`. Every gameplay edit goes through `state.blockChanges.set(x,y,z,block)`, which writes the voxel, relights, records the save delta in `changedBlocks`, and appends to the per-tick `editJournal`. `serialize().changes` and `blockChanges.changes()` both read `changedBlocks`. **Only `blockChanges.set` feeds the `changes` journal** — a raw `world.set` does not — so that is the only path to worry about.

The RNG is the crux: `GameEngine.ts:289` → `this.rng = options.rng ?? Math.random`. **All three production construction sites** (`useMinecraftGame.ts:276`, `server/room.ts:172`, `NetworkSession.ts:253`) pass **no `rng`**, so the live simulation uses **`Math.random` — fully nondeterministic**. Only unit tests inject a seeded rng. Worldgen itself is seeded/deterministic (`generation.ts` `rand`), but the *simulation* tick RNG is not.

Tick loop: the browser shell uses `createAccumulator` (`tickDriver.ts:39`, frame-delta catch-up, ≤0.05s/step, ≤5 substeps = ≤0.25s/frame, excess dropped). It is **not a fixed count of ticks** — total simulated seconds ≈ wall time since mount.
