## 4. Cloud saves — `lib/game/cloudSaves.ts`

**Interaction with the local write path (ordering &amp; newness):**

## 5. Save blob shape &amp; size

**Shape** (`SaveData`, `lib/game/types.ts:389-408`; built by `GameEngine.serialize()` at `engine/GameEngine.ts:1174-1191`):

```
  mobs: SavedMob[], vehicles: SavedVehicle[], villagesSeeded: true

```
`SavedPlayer` at `types.ts:365-380`; the full versioned type chain is `SaveDataV1`…`SaveDataV16` then `SaveData` (v17) at `types.ts:144-408`. There have been **17 schema versions**; `readSave` migrates any older blob forward on load.

**Encoding / size:**
- **The world diff (`changes`) is a plain JSON array of `[voxelIndex, blockId]` number pairs** — computed by `createBlockChangeTracker().changes()` = `[...changedBlocks.entries()]` (`engine/blockChanges.ts:67-69`). **No RLE, no base64, no bit-packing.** It's stored as **delta-against-worldgen-baseline**: a block restored to its generated value drops out of the set (`blockChanges.ts:48-51`), so an untouched world serializes to `changes: []`.
- **Local persistence is uncompressed** — `writeSave` does `JSON.stringify(data)` straight into localStorage (`save.ts:363`). So on-disk size is roughly the JSON text length; each block edit costs ~8-15 chars (e.g. `[1234567,42],`). A heavily-terraformed world can reach hundreds of KB to low MB of JSON. Inventory/mobs/containers are small by comparison.
- **Cloud persistence is gzipped** — the same blob through `gzipJson` (`cloudSaves.ts:37-40`), and the server rejects anything over **4 MiB gzipped** (`save/route.ts:40`). The `[idx,block]` integer stream compresses very well.

**Relevance to an IndexedDB move:** the write is a single synchronous `localStorage.setItem(JSON.stringify(...))` with **no quota guard**, called from four sync contexts including `beforeunload` and the effect-cleanup teardown (`:496-498`) and the in-app-nav `quitToWorlds` (`:656`); the read is a single synchronous `getItem`+`JSON.parse` on the render-commit path inside `attachMount` (`:258`) feeding the `GameEngine` constructor. Implication for your migration: no UI reads the save blob to render the world list, so an async IndexedDB blob read is compatible with the existing synchronous manifest-driven list. The blob is only touched at boot (already in a commit callback), in cloud-upload, and in `loadNow` (which currently over-reads for a mere presence check).

## 7. Test environment &amp; IndexedDB

- **Env setup**: `bunfig.toml` → `[test] preload = ["./tests/setup.ts"]`. `tests/setup.ts` (24 lines) captures native `fetch`/`WebSocket` before happy-dom overrides them (line 10), then `GlobalRegistrator.register()` (line 15) from `@happy-dom/global-registrator` v20.10.2, and registers a `@testing-library/react` `cleanup()` in `afterEach` (19–23). No other preload/setup file; no polyfills registered.
- **happy-dom does NOT provide IndexedDB.** happy-dom v20.10.2 (`node_modules/happy-dom`) has no IndexedDB implementation: `node_modules/happy-dom/lib/` has no `indexed`/`idb` directory, and grep for `indexeddb` across the entire `node_modules/happy-dom/` and `node_modules/@happy-dom/` trees returns **no matches**. So after `GlobalRegistrator.register()`, `globalThis.indexedDB` / `IDBFactory` are undefined — IDB-backed code will throw under `bun test` unless a polyfill is added.
- **No polyfill present.** No `fake-indexeddb` (or any `idb` package) in `package.json` devDependencies; no global registration anywhere. The current save tests dodge this entirely by injecting a Map-backed `Storage` fake into `readSave`/`writeSave` rather than touching any browser storage global.
- **Bun-native globals that DO work in tests**: `CompressionStream`/`DecompressionStream` (used by `cloudSaves.ts` 38/43 and exercised by `cloudSaves.test.ts`) resolve from Bun's runtime, not happy-dom — so Bun does provide those Web Streams globals, but **not** IndexedDB.

Branch: `feature/idb-saves` off `main`. Scope: ONLY the `minecraft_world_save_&lt;worldId&gt;` blobs move to IndexedDB. Manifests (`minecraft_profiles_v1`, `minecraft_worlds_v1`), prefs, cloud stamps, and the session pointer stay in localStorage. SaveData stays v17 — only the container moves.

## 1. Core design decisions (with rationale)

**D1 — Store the SaveData object (structured clone), not a JSON string.**
Refactor `lib/game/save.ts` to extract the pure validate+migrate chain as `parseSave(value: unknown): SaveData | null`; `readSave(key, storage)` becomes `parseSave(JSON.parse(storage.getItem(key)))` with the same try/catch → null semantics. Rationale:
- The server's sync `readSave` path (`server/persistence.ts:37` one-key Storage shim) keeps working byte-for-byte unchanged.
- IDB reads skip a `JSON.parse` of a multi-hundred-KB string on boot; writes skip `JSON.stringify` in the unload handler (structured clone happens inside `put()` — roughly the same cost, but only one serialization instead of stringify-then-clone).
- `GameEngine.serialize()`/`serializePlayer` (verified at `GameEngine.ts:1174-1191`, `:1130-1147`) produce only plain objects/arrays/numbers/strings/null — structured-clone-safe, no THREE vectors leak through.
- Corruption/tamper safety is unchanged: every IDB read still flows through `parseSave` (full v1→v17 migration + validation), so a hand-edited or truncated record degrades to `null` exactly like today.

**D2 — Hand-rolled IDB wrapper, injectable async store, localStorage-adapter fallback.**
One DB `minecraft` (matches the `minecraft_*` key family), one object store `worldSaves`, IDB version 1, keyed by raw `worldId` (including synthetic `cloud:&lt;id&gt;` ids — they're plain strings, valid IDB keys). No `idb`/`dexie` dependency. If `indexedDB` is undefined or `open()` rejects (private modes), the store flips permanently (for the session) to a localStorage-backed adapter using the existing `worldSaveKey(id)` keys — i.e., degraded mode is exactly today's behavior, including today's quota risk.

**D3 — Per-key write queue with latest-wins coalescing; reads are read-your-writes.**
The store keeps `latest: Map&lt;worldId, SaveData | null&gt;` (null = tombstone) set synchronously on every `write`/`remove`, plus a single in-flight flusher per key. `read()` short-circuits to `latest` when present — so a remount read can never see a stale blob regardless of IDB timing. This solves hard problem 2 without touching React commit ordering: React runs the old mount's cleanup (which enqueues the write synchronously) before the new mount's effects (which issue the read).

**D4 — Boot read moves to GameShell (option a): a `WorldSaveGate` preloads the blob and passes it down as a prop.**
`attachMount` stays synchronous; `new GameEngine({ save: initialSave, ... })`. Chosen over async-attachMount because: it mirrors the existing cloud-adopt preload (already async in `openWorld`/`playCloud`); it avoids StrictMode/cancellation hazards in the callback ref (`reactStrictMode: true` is on — verified in `next.config.mjs`); and the Load/Reset reload-nonce flow slots in cleanly by moving the existing React `key` from `MinecraftGame` up onto the gate, so a nonce bump unmounts the old game (enqueueing its write or skipping via `skipUnmountSaveRef`) before the gate's fresh read — which the queue then orders correctly.

**D5 — Unload flush: replace `beforeunload` with `pagehide` + `visibilitychange→hidden`, starting the IDB put synchronously; NO localStorage emergency mirror.** Full justification in §4.

**D6 — Migration: lazy per-key copy-then-delete on read, plus an eager background sweep at GameShell mount.** Details in §3.

### `lib/game/idbKv.ts` (~80 lines, client-safe: no `indexedDB` touched at module top level)

```ts
export type AsyncKv = {
  /** Resolves false when IDB is unusable here (missing global, open() failed). */
  ready(): Promise&lt;boolean&gt;;
  get(key: string): Promise&lt;unknown&gt;;                 // undefined when absent
  put(key: string, value: unknown): Promise&lt;void&gt;;    // resolves on tx.oncomplete (durable)
  delete(key: string): Promise&lt;void&gt;;
  /** Starts a put synchronously on an already-open connection (unload path). False if not open. */
  tryPutSync(key: string, value: unknown): boolean;
};
export function createIdbKv(dbName: string, storeName: string, factory?: IDBFactory): AsyncKv;
```

Implementation notes:
- Lazy `open()` on first op, cached connection promise. `onupgradeneeded` → `createObjectStore(storeName)`. `onclose`/`onversionchange` → null the cached connection so the next op reopens.
- `put`/`delete` resolve on `transaction.oncomplete` (not request `onsuccess` — request success fires before durable commit; the "Saved" toast must mean committed).
- `factory` param is the test seam for `fake-indexeddb`'s `IDBFactory` — no global registration needed.

### `lib/game/saveStore.ts` (~150 lines)

```ts
export type WorldSaveStore = {
  read(worldId: string): Promise&lt;SaveData | null&gt;;
  write(worldId: string, data: SaveData): Promise&lt;void&gt;;  // queued, latest-wins; resolves when durable
  remove(worldId: string): Promise&lt;void&gt;;
  /** Unload-safe fire-and-forget: begins the IDB put synchronously when possible. */
  flushWrite(worldId: string, data: SaveData): void;
  /** Copies every localStorage `minecraft_world_save_*` blob into IDB (idempotent sweep). */
  migrateAll(): Promise&lt;void&gt;;
};
export function createWorldSaveStore(deps?: { kv?: AsyncKv; storage?: Storage }): WorldSaveStore;
/** App-wide singleton (lazily builds its kv on first use — SSR-import safe). */
export const worldSaves: WorldSaveStore;
export function requestPersistentStorage(): void;  // opportunistic navigator.storage.persist()
```

Semantics:
- **read(id)**: (1) if `latest` has an entry → return it (tombstone → null). (2) `kv.get(id)` → if a record exists → `parseSave(record)`. (3) LS fallback: `readSave(worldSaveKey(id), storage)` → if non-null, migrate this key (§3) and return it. (4) null.
- **write(id, data)**: set `latest`, kick the per-key flush loop (`put` whatever is latest at execution time; on success, if `latest` still holds that exact value, clear it AND opportunistically `storage.removeItem(worldSaveKey(id))` — a lingering un-migrated LS copy is now stale, deleting it both prevents shadow-resurrection and frees quota on the first save). Returned promise resolves when this-or-newer data is durable.
- **remove(id)**: synchronously `storage.removeItem(worldSaveKey(id))` (cheap, closes the LS-shadow window immediately), set tombstone in `latest`, enqueue `kv.delete`.
- **flushWrite(id, data)**: set `latest` (so any racing read sees it), then `kv.tryPutSync(id, data)`; if the connection isn't open (never warmed / browser closed it), fall back to `void write(...)` — best effort.
- **Fallback mode**: if `await kv.ready()` is false (checked once, memoized), all ops go straight to `storage` under `worldSaveKey(id)` via `readSave`/`writeSave` — current behavior preserved verbatim, quota throws surface as rejected `write()` → "Save failed" toast, same as today.
- `requestPersistentStorage`: `void navigator.storage?.persist?.().catch(() =&gt; {})`, guarded for SSR/tests.

No import cycles: `saveStore` imports `save.ts` (parseSave/readSave/writeSave) and `worlds.ts` (`worldSaveKey`, `WORLD_SAVE_PREFIX`); neither imports it back (`worlds.ts` gains a lazy `import("./saveStore")` — see §5).

## 3. Migration mechanism &amp; failure semantics

Mirrors `legacyMigration.ts` copy-then-delete semantics per key:

1. Copy: `await kv.put(id, parsed)` — LS original untouched until this durably commits.
2. Verify implicitly via `put` resolving on `tx.oncomplete`.
3. Delete: `storage.removeItem(worldSaveKey(id))` inside its own try/catch (a failed delete just leaves a shadowed, quota-wasting copy that the next successful `write()` cleanup removes).

Failure semantics:
- IDB put fails mid-migration → LS blob remains authoritative; `read` returned the parsed data anyway (play proceeds); next read retries the migration. **During any transitional/failed state, reads find the blob** because the read order is IDB-record-presence first, LS fallback second.
- Corrupt LS blob (`readSave` → null) → return null, leave the blob in place (never destroy data we couldn't parse).
- Idempotent: re-running sees the IDB record and no-ops. Concurrent lazy-read-migration + sweep on the same key serialize through the per-key queue of the shared singleton.

**Eager sweep** `migrateAll()`: iterate `localStorage` **by key prefix** `WORLD_SAVE_PREFIX` (index iteration, not the worlds manifest — this also catches `cloud:&lt;id&gt;` blobs, which have **no manifest entry**, and orphans), migrating sequentially. Fired (fire-and-forget, try/caught) from the GameShell mount effect right after `migrateLegacySave()` — which deliberately still writes to localStorage (it's sync, Storage-injectable, and fully tested); the sweep picks its output up immediately. No presence flag needed: emptiness of the prefix scan is the natural terminal state, and per-key idempotency makes re-runs free.

## 4. Unload-save design

Replace the `beforeunload` → `autoSave` registration (`useMinecraftGame.ts:397`) with:

```ts
const flushSave = () =&gt; {
  if (online) return;
  worldSaves.flushWrite(worldId, gameEngine.serialize());  // silent — no toast
  syncCloudSave(gameEngine, true);
};
const onVisibility = () =&gt; { if (document.visibilityState === "hidden") flushSave(); };
window.addEventListener("pagehide", flushSave);
document.addEventListener("visibilitychange", onVisibility);
```

(Deregister both in the cleanup; the 15s interval autosave keeps its "Saved" toast; the flush is silent so tab-switching doesn't toast-spam — but `syncCloudSave` keeps `notify=true` so a rare cloud conflict still warns when the player returns.)

Browser-behavior justification:
- **Unload event order** (all modern engines): `beforeunload` → `visibilitychange(hidden)` → `pagehide` → `unload`. `visibilitychange→hidden` and `pagehide` both fire on reload and same-tab navigation — so the e2e "plain reload persists" flow is covered twice; the claim in the brief is correct.
- **Mobile coverage**: iOS Safari and Android background-kill never reliably fire `beforeunload`; `pagehide` is the reliable navigation/close signal on iOS, and `visibilitychange→hidden` is the Page-Lifecycle-recommended "last reliable moment" for app-switch (which happens seconds-to-minutes before a background process kill — the put has ample time). This *shrinks* today's mobile data-loss window from ≤15s (autosave only) to ~0 on app-switch.
- **Does an IDB put started in the handler commit?** Two layers: (1) Chromium and Firefox complete transactions that were created with requests queued before document teardown (the backing-store work continues in the browser process); WebKit does in current versions, historically flakier. (2) Independent ordering guarantee for the reload case: IDB readwrite transactions on the same object store acquire scope locks **in creation order across connections**, so the new document's boot-read transaction queues behind the old document's write transaction — the reload can't read-around the write; the only failure mode is the write tx being aborted outright.
- **bfcache bonus**: dropping `beforeunload` improves back/forward-cache eligibility (Safari/Firefox disqualify pages with beforeunload handlers) — relevant for the PWA. On a bfcache restore, `pageshow` resumes the still-mounted game; the interval keeps running; no handler changes needed.
- **Emergency localStorage mirror: rejected.** It reintroduces the quota throw for exactly the oversized worlds being rescued, and a successful mirror next to a successful IDB put leaves a stale LS copy that the LS-fallback read path could resurrect later (e.g. after a partial site-data clear), silently rolling the world back. The residual risk (a browser aborting an unload-started tx) is bounded by the 15s autosave plus the earlier `visibilitychange` flush.
- **Connection warmth**: `tryPutSync` needs an open connection; the boot read (shell preload) opens it long before any unload. If the browser closed it (`onclose`), flushWrite degrades to an async `write` — best effort, backstopped by autosave.

## 10. Risks &amp; open questions for you to decide

1. **Unload-commit residual risk** (flagged, accepted?): an IDB tx started in `pagehide` is not spec-guaranteed to commit; in practice Chromium/Firefox/modern WebKit complete it, the reload case is additionally protected by cross-connection tx ordering, and worst-case loss is bounded by the 15s autosave + the earlier `visibilitychange` flush.
